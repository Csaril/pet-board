# Многокомнатная архитектура Tabletop Board

Статус документа: **этапы 1–4 реализованы**. Сервер обслуживает несколько независимых
комнат: есть `catalog.sqlite`, `server-secret`, CLI управления, `RoomManager` с
ленивым открытием и LRU, комнатные cookie и полная изоляция HTTP/WebSocket.
Реализованы также manifest v2, backup/restore по комнате, копия каталога, полная
копия установки и физическое удаление комнаты с сохранением копий в
`data/deleted-rooms/`. **Не реализована отложенная загрузка системных модулей** — PbtA и
Nechronica по-прежнему статически импортируются; это следующий отдельный этап.

Документ фиксирует фактическое состояние, аудит загрузки системных модулей,
сравнение вариантов хранения и поэтапный план перехода. Ленивая загрузка модулей
описана только как план, а не как готовая функциональность.

---

## 1. Текущее состояние (по коду, не по документации)

- Один процесс Fastify обслуживает несколько комнат. Комната определяется по коду
  при входе и по `roomId` в URL/запросе, а затем проверяется по каталогу и сессии.
- `data/catalog.sqlite` — каталог комнат. Поля: `id`, `name`, `system_id`,
  `system_version`, `room_code_hmac`, `gm_password_hash`, `status`
  (`active`/`disabled`/`archived`), `created_at`, `updated_at`. Игровых данных в
  каталоге нет.
- `data/server-secret` — 32+ случайных байта, права `0600`. Создаётся только при
  инициализации. Если каталог существует без секрета, сервер завершается с
  понятной ошибкой и не перегенерирует секрет.
- `AppConfig` больше не требует `ROOM_NAME`/`ROOM_CODE`/`GM_PASSWORD` для обычного
  запуска. Эти поля читаются только `rooms:init` для первичной регистрации старой
  комнаты `default`. `MAX_OPEN_ROOMS` задаёт лимит одновременно открытых баз.
- `RoomManager` открывает комнаты лениво, при первом lease. Он проверяет статус
  по каталогу, сверяет `system_id`/`system_version` с `room.sqlite`, защищает путь
  от traversal, ведёт refcount и LRU. Простаивающие комнаты закрываются, при
  переполнении возвращается `RoomCapacityError`, а не открывается безлимит.
- `RoomStore` получает **каталог конкретной комнаты**. В текущей установке это
  `data/rooms/default/` для мигрированной комнаты и `data/rooms/<uuid>/` для
  новых. База лежит в `<roomDir>/room.sqlite`, ресурсы — в `<roomDir>/assets`,
  копии — в `<roomDir>/backups`. Глобального «текущего RoomStore» нет.
- Старая раскладка `data/room.sqlite` + `data/assets` + `data/backups` не
  открывается сервером: требуется однократная команда `npm run room:migrate`,
  затем `npm run rooms:init`.
- Кука называется `tb_session_<roomId>` и содержит непрозрачный токен; сервер
  хранит только его SHA-256 (`sessionDigest`) в `sessions` этой комнаты.
  `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` при HTTPS. Выход из одной
  комнаты не затрагивает cookie и сессии других комнат.
- Участник и сессия разделены: `participants(id, name, role)` — стабильная
  сущность, `sessions(id, participant_id, expires_at)` — браузерный вход. На
  `participants.id` ссылаются `character_sheets.assigned_player_id`,
  `notes.owner_id`, `asset_uploaders.participant_id`, `dice_rolls.author_id/actor_id`.
  Один участник может иметь несколько сессий; старые `sessions.id` сохранены как
  `participants.id`.
- Система комнаты закрепляется один раз. Новые поля `room.system_id`,
  `room.system_version`, `room.module_config_json`, `room.system_fixed` заменяют
  изменяемую пару `active_system_id/version`. Одноразовая команда —
  `room:system:initialize` (WS) или `PUT /api/room/system` (HTTP); устаревшая
  `room:system:set` всегда отклоняется с `409 ROOM_SYSTEM_IMMUTABLE`.
- `system_fixed = 0` означает «система ещё не выбрана»; `system_fixed = 1` при
  `system_id IS NULL` — намеренный режим «без системы». Формат листов при выборе
  не мигрирует, листы другой системы скрываются из обычных API.
- `dice_rolls.system_id/system_version` фиксируют серверную атрибуцию новых
  системных событий; свободные броски остаются `NULL/NULL`. Старые
  `pbta`/`ability-use` записи получают `pbta-2d6` без выдуманной версии и
  показываются как исторические.
- Каталог читается на каждом запросе и сообщении, поэтому `rooms:disable`,
  `rooms:enable` и `rooms:archive` из другого процесса обнаруживаются без
  перезапуска сервера. WebSocket-соединения недоступной комнаты закрываются.

### Таблицы `room.sqlite`

| Таблица | Назначение | Ключевые связи |
| --- | --- | --- |
| `room` | единственная строка `id = 1`: имя, фон, сцена, закреплённая система | — |
| `sessions` | браузерные сессии | `participant_id` (`CASCADE`), `expires_at` |
| `participants` | стабильные участники комнаты | `name`, `role` |
| `dice_rolls` | последние 10 бросков (общая история) | `author_id`, `actor_id`, `character_id`, `ability_*`, `system_id/version` |
| `board_layers` | слои основной доски и боя | `scene` |
| `assets` | библиотека изображений | `UNIQUE(sha256, mime_type)` |
| `board_objects` | объекты на слоях | `asset_id`, `layer_id` (`RESTRICT`) |
| `notes` | заметки и метки | `marker_asset_id`, `owner_id` |
| `note_assets` | вложения заметок | `note_id`, `asset_id` |
| `note_markers` | метки заметок на слоях | `note_id` (`CASCADE`), `layer_id` |
| `stickers` | текстовые стикеры | `layer_id` |
| `asset_uploaders` | кто загрузил ресурс | `asset_id`, `participant_id` |
| `character_sheets` | листы персонажей | `system_id`, `system_version`, `portrait_asset_id`, `assigned_player_id` |
| `character_counters` | счётчики листа | `sheet_id` (`CASCADE`) |
| `character_abilities` | способности листа | `sheet_id` (`CASCADE`), `asset_id` |

Миграции схемы выполняются императивно в конструкторе `RoomStore` (`ALTER TABLE`,
пересоздание таблиц). Отдельной таблицы версии схемы нет.

### Существующий backup/restore

`server/backup-lib.ts` копирует `room.sqlite` и `assets/` в `<roomDir>/backups/<name>`.
Manifest v2 содержит `roomId`, `roomName`, `systemId`, `systemVersion`,
`schemaVersion` и SHA-256 файлов. Restore сверяет комнату и системную пару,
создаёт `pre-restore-*` и заменяет файлы атомарно. Копии `version: 1` читаются,
но требуют явной целевой комнаты. Отдельно `server/catalog-backup.ts` копирует
`catalog.sqlite` + `server-secret` и умеет создавать проверяемую копию всей
установки; restore каталога выполняется только при остановленном сервере.

## 2. Аудит загрузки System Modules

### Что загружается сейчас

- `src/modules/registry.ts` статически импортирует `pbtaSystemModule` и
  `nechronicaSystemModule`.
- `src/client/app.ts` импортирует реестр и модуль PbtA; серверные `store.ts`,
  `sheets.ts`, `index.ts` импортируют PbtA напрямую.
- Динамических `import()` нет. Отдельных чанков для систем нет.
- Метаданные обеих систем доступны до входа в комнату. Код PbtA (схема листа,
  расчёт броска, подписи характеристик) и descriptor Nechronica попадают в
  начальный JS-чанк.

### Измерения

- Начальный JS: **292 601 байт** (~286 КиБ), gzip — **84 650 байт** (~82,7 КиБ).
- Konva (minified) — ~193 КБ, то есть основная часть бандла.
- Исходники систем: `pbta-2d6/module.ts` — 1 996 Б, `roll.ts` — 2 936 Б,
  `nechronica/module.ts` — 492 Б, `registry.ts` — 967 Б; всего ~6,4 КБ.
- В собранном чанке присутствуют строки обеих систем (`Могущество`,
  `Некорректный бонус характеристики`, `Nechronica`, `Сила Судьбы`).
- Точный вклад каждого модуля без bundle analyzer не измерялся. По исходникам
  вклад Nechronica сейчас меньше 1 КБ; вклад PbtA — несколько КБ. Выигрыш от
  разделения бандла сегодня небольшой, но архитектурно важен для будущих систем.

### Что выполняется/загружается лишнего

- Код обеих систем парсится и выполняется при старте.
- Данные листов не грузятся до входа, но клиент запрашивает листы закреплённой
  системы после входа; сервер уже фильтрует их по `room.system_id/version`.
- История бросков не фильтруется по системе: `getDiceRolls()` возвращает
  последние 10 записей комнаты независимо от `kind`/системы. Записи без
  совпадающей системной атрибуции остаются видимыми как «Историческая запись»,
  не запускают механику и не могут быть повторены.
- Ресурсы грузятся по требованию (по ID), но каталог ресурсов и данные комнаты
  не разделены между комнатами, потому что комната одна.

## 3. Сравнение вариантов хранения

### A. Отдельная SQLite на комнату + `catalog.sqlite`

Плюсы:
- Изоляция на уровне файла: забытый `WHERE room_id = ?` не может отдать чужие данные.
- `RoomStore` уже принимает каталог комнаты (`roomDir`); достаточно передать ему каталог другой комнаты.
- Backup/restore, удаление и перенос комнаты — операции над каталогом.
- Ресурсы и резервные копии лежат рядом с БД комнаты.
- Падение/повреждение одной БД не блокирует остальные комнаты.
- Схемные миграции можно запускать при открытии конкретной комнаты.

Минусы:
- Несколько открытых соединений `better-sqlite3`; нужен пул/LRU и закрытие простаивающих.
- Административные запросы «по всем комнатам» идут через каталог и обход комнат.
- Общая дедупликация ресурсов между комнатами сложнее (в v1 не нужна).

### B. Одна SQLite с `room_id` во всех таблицах

Плюсы:
- Одно соединение, проще глобальные отчёты и общий backup.
- Одна миграция схемы на весь сервер.

Минусы:
- Каждый из десятков запросов `RoomStore` обязан фильтровать `room_id`; любая
  забытая фильтрация — утечка листов, заметок, истории бросков или ресурсов.
- Составные внешние ключи (`room_id, id`) и индексы во всех таблицах.
- Восстановление одной комнаты из общей БД — выборочная операция, а не замена файла.
- Удаление комнаты требует каскадной очистки и проверки ссылок на ресурсы.
- Текущий `RoomStore` придётся переписать почти целиком, риск регрессий выше.

### Рекомендация

**Вариант A**: `data/catalog.sqlite` + `data/rooms/<room-id>/room.sqlite`,
`assets/`, `backups/`. Он лучше соответствует текущему коду, даёт сильную изоляцию
и позволяет сохранить существующие backup/restore и `RoomStore` с минимальными
изменениями. Глобальную дедупликацию ресурсов не вводить в первой версии.

Этап 3 реализовал левую часть схемы без каталога: единственная комната имеет
постоянный ID `default`, который хранится в `data/storage.json`. Каталог комнат
сможет сослаться на этот же ID и каталог без повторного переноса базы.

## 4. Рекомендуемая архитектура

### 4.1 Каталог

`data/catalog.sqlite`:

```sql
CREATE TABLE rooms (
  id TEXT PRIMARY KEY,                 -- UUID или legacy "default", не меняется
  name TEXT NOT NULL,
  system_id TEXT,                      -- NULL допустим только при особой миграции
  system_version TEXT,
  room_code_hmac TEXT NOT NULL UNIQUE, -- HMAC(нормализованный код, server-secret)
  gm_password_hash TEXT NOT NULL,      -- scrypt + соль
  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'disabled', 'archived')),
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX rooms_status ON rooms(status);
```

- Код комнаты не хранится открытым: для поиска используется HMAC с секретом
  сервера (`data/server-secret`, права `0600`). Короткий код нельзя безопасно
  хранить обычным хешем — он перебирается офлайн.
- Пароль GM — медленный KDF (scrypt) с индивидуальной солью, сравнение
  constant-time.
- `system_id`/`system_version`/`system_fixed` в каталоге дублируются в
  `room.sqlite` и защищаются триггером от изменения. Выбор делается один раз:
  `system_fixed = 0` — ещё не выбрано, `system_fixed = 1` + `NULL/NULL` —
  намеренный режим без системы. Каталог и база должны совпадать, иначе комната
  не открывается.

### 4.2 Комната

`data/rooms/default/room.sqlite` — все игровые данные. Изоляция каталога и
разделение участников уже выполнены в единственной комнате:

- `participants(id, name, role, created_at)` и
  `sessions(id, participant_id REFERENCES participants(id) ON DELETE CASCADE,
  expires_at, created_at)`. Старые ID участников сохранены при миграции.
- `room.system_id`, `room.system_version`, `room.module_config_json`,
  `room.system_fixed`; триггеры `room_system_immutable`,
  `room_system_fixed_immutable`, `room_legacy_system_immutable`,
  `room_system_pair_update` запрещают обычную смену закреплённой пары.
- `dice_rolls.system_id`, `dice_rolls.system_version` с серверной атрибуцией;
  исторические записи не получают выдуманную версию.
- `character_sheets` с `system_id/system_version/schema_version`; листы другой
  системы сохраняются, но скрываются из обычных API.

Остаётся на будущее:

- `room_schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT)` для
  явных миграций версии схемы комнаты; сейчас миграции по-прежнему императивные.
- `payload_json` для листов только если понадобится формат, не выражаемый
  текущими колонками.

`room-config.json` не нужен: код, имя, система и пароль комнаты хранятся в
`catalog.sqlite`, а `room.sqlite` остаётся единственным источником игровых данных.

### 4.3 Маршрутизация и сессии

Реализовано:

- `POST /api/session` принимает `roomCode`, имя, роль и пароль GM. Сервер ищет
  комнату по HMAC кода в каталоге, проверяет статус, пароль (только для GM) и
  открывает `RoomStore` через lease. Ошибка входа нейтральна и не перечисляет
  комнаты; попытки ограничены rate limit.
- Клиент после входа переходит на `/room/<room-id>`. Cookie называется
  `tb_session_<roomId>`; сервер проверяет и комнату, и сессию. `roomId` из
  query/заголовка сверяется с каталогом и cookie, а не принимается на веру.
- HTTP API сохраняет прежние пути. Для комнаты, найденной по cookie, `roomId`
  можно не дублировать; если он передан, он должен совпадать.
- WebSocket `/ws?roomId=<id>` резолвит комнату по cookie и query; сокеты
  группируются по `roomId + sessionId`, рассылка `room:state` идёт только
  участникам комнаты. Соединение держит lease на комнату.
- Переключение комнаты = новый вход в другой вкладке; клиент сбрасывает
  локальное состояние, ключи `localStorage` включают `roomId` (камера, панели,
  тема, открытый лист, прочитанные события).

### 4.4 Управление комнатами

Реализован CLI, веб-админки нет:

```text
npm run rooms:init
npm run rooms:create -- --name "..." --system pbta-2d6
npm run rooms:create -- --name "..." --system nechronica
npm run rooms:list
npm run rooms:disable -- <room-id>
npm run rooms:enable -- <room-id>
npm run rooms:archive -- <room-id>
npm run rooms:delete -- <room-id> [--force] [--yes] [--no-backup]
```

- `create` атомарен: временный `rooms/.creating-*`, затем rename; запись в
  каталог появляется только после успешного создания и проверки системы.
  Пароль вводится скрыто в TTY или одной строкой через stdin; кода в аргументах
  нет, чтобы он не попал в историю shell.
- `list` не печатает коды, HMAC и хэши. `archive` создаёт финальную копию,
  закрывает соединения и сохраняет данные.
- `delete` удаляет каталог комнаты и запись каталога. Активная или отключённая
  комната требует `--force`; архивная удаляется без него. Подтверждение — точный
  ID комнаты либо `--yes`. По умолчанию создаётся финальная копия, а все backups
  переносятся в `data/deleted-rooms/<id>-<время>/` с `room.json`;
  `--no-backup` отключает только новую финальную копию. Копию можно восстановить
  в новую комнату той же системы через `backup:restore --accept-room-mismatch`.
- Каталог читается на каждом запросе, поэтому изменения статуса видны
  работающему серверу без перезапуска.

### 4.5 Изоляция данных

- Каждый ресурс принадлежит комнате: файл лежит в `rooms/<id>/assets/<asset-id>`.
- Выдача файла: сначала проверка строки `assets` в БД **этой** комнаты, затем
  чтение файла. Знание ID чужого ресурса бесполезно.
- Удаление проверяет ссылки (`board_objects`, `notes`, `note_assets`,
  `character_sheets`, `character_abilities`) в пределах комнаты.
- Дедупликация SHA-256 — внутри комнаты (`UNIQUE(sha256, mime_type)` уже это даёт).
- Листы фильтруются по комнате (файл БД) и по `system_id/system_version`.
- История бросков и WebSocket-рассылка — только в пределах комнаты.
- Сессии привязаны к комнате; чужой `roomId` в куке не даёт доступа.

### 4.6 Отложенная загрузка модулей

- В ядре — только метаданные: `{ id, version, name, capabilities }`.
- Клиент: явная карта загрузчиков, без интерполяции пользовательских строк:
  `() => import('./system/pbta-2d6/client.js')`. Загрузка после получения
  `room:state` с `systemId/systemVersion`; кэш `Promise` по `id@version`;
  `mount/dispose` при смене комнаты.
- Сервер: такая же явная карта `() => import('./system/.../server.js')`;
  загрузка по ID из каталога, кэш на процесс. Node кэширует ES-модули, поэтому
  выгрузки из памяти не обещаем; один экземпляр кода обслуживает все комнаты
  одной версии.
- Модуль не хранит состояние комнаты в module-level переменных: конфиг, store и
  identity передаются аргументами.
- Точная версия обязательна. Если комната закреплена за версией, которой нет в
  сборке, сервер отказывается открывать комнату (или требует явную миграцию).
  Каталоги версий: `system/pbta-2d6/1.0.0/`.
- Обновление модуля: новая комната получает новую версию; существующая —
  только через `rooms migrate-system` с резервной копией и зарегистрированными
  миграциями `sheet_schema_version`.

## 5. План перехода

### Этап 1. Боевая карта (выполнено)

- Причина: на узкой ширине группа «Боевая карта» переносится в меню «Ещё».
  `toggleMenu` вызывал `closeMenus()`, который скрывал родительское меню, а

- Тест: сценарий 29 в `server/ux.test.ts`; ручная проверка на 900 и 1400 px.
- Затрагиваемые файлы: `src/shared/menu.ts`, `src/client/app.ts`, `server/ux.test.ts`.
- БД/API/WebSocket не менялись.

## 6. Перенос старых данных

Фактический маршрут для уже существующей установки:

1. Остановить сервер. Сделать резервную копию всего `data/` вручную (старые
   комнатные копии находятся в `data/backups/`, новые — в
   `data/rooms/*/backups/`).
2. Если данные лежат в старой раскладке (`data/room.sqlite`, `data/assets`),
   выполнить `npm run build` и `npm run room:migrate`. Команда переносит всё в
   `data/rooms/default/`, проверяет БД, ресурсы и создаёт проверочную копию.
3. Заполнить `ROOM_NAME`, `ROOM_CODE`, `GM_PASSWORD` в `.env` и выполнить
   `npm run rooms:init`. Комната `default` регистрируется в `catalog.sqlite`
   с уже закреплённой системой; код и пароль сохраняются только как HMAC/scrypt.
   Повторный запуск идемпотентен и не меняет секреты.
4. Проверить `npm run rooms:list`, войти в `default` по старому коду и убедиться,
   что объекты, ресурсы, заметки, листы, броски и боевая карта на месте.
5. После успешной проверки `.env` можно очистить от `ROOM_CODE`,
   `GM_PASSWORD`, `ROOM_NAME`: обычный сервер их больше не использует. Старый
   `data/` не удалять до отдельного решения.

Старые сессии не переносятся в комнатную cookie-модель: пользователи один раз
входят заново. Это осознанное решение — старая `tb_session` не содержит комнаты
и не может безопасно определить её в многокомнатной установке.

Новая комната создаётся сразу в правильной раскладке:

```sh
npm run rooms:create -- --name "Новая кампания" --system pbta-2d6
```

### Судьба листов нескольких систем

- Не удалять и не «исправлять» автоматически.
- Листы другой системы остаются в `character_sheets`, но скрыты из обычных API
  и не редактируются.
- Если GM хочет продолжить игру в другой системе — создать отдельную комнату.
  Перенос листов между комнатами и конвертация систем не реализованы.
- Архив как отдельное хранилище и read-only экспорт — возможное расширение, а
  не текущая функциональность.

## 7. Риски и открытые вопросы

1. **ID сессии больше не равен ID участника (решено на этапе 3).** Старые
   `sessions.id` перенесены в `participants.id`, поэтому назначения листов,
   заметки и загрузчики сохранили ссылки. При дальнейших миграциях нельзя
   пересоздавать participant ID; новые сессии получают собственные ID.
2. **Короткий код комнаты (решено на этапе 4).** Используются HMAC-SHA256 с
   `server-secret`, нормализация и rate limit; открытый код не хранится.
   Смена кода — отдельная явная операция, автоматически не реализована.
3. **Секреты в `.env` (решено для обычного запуска).** После `rooms:init`
   комнатные секреты живут в каталоге, а `.env` нужен только для первичной
   регистрации `default`. `.env.example` и README объясняют переход.
4. **`better-sqlite3` синхронный (решено базово).** `RoomManager` держит LRU,
   refcount и лимит `MAX_OPEN_ROOMS`; при дальнейшем росте нагрузки возможны
   отдельные процессы, но это уже горизонтальное масштабирование.
5. **Кэш ES-модулей (не реализовано).** Код системы нельзя выгрузить; будущая
   ленивая загрузка примет один экземпляр на версию и потребует отсутствия
   состояния в модуле. Сейчас оба модуля грузятся статически.
6. **Точные версии модулей (частично решено).** `RoomManager` отказывается
   открывать комнату, если системы нет в сборке. Политика хранения старых
   версий и контролируемая миграция версии ещё не реализованы.
7. **Backup во время записи (решено).** Используется SQLite online backup API,
   manifest v2 и checksums; restore проверяет копию и создаёт `pre-restore-*`.
8. **Ресурсы и дедупликация (решено для комнаты).** Дедупликация и проверка
   ссылок действуют внутри комнаты. Глобальная дедупликация не реализована и
   потребует отдельного реестра ссылок.
9. **Локальное состояние браузера (решено на этапе 4).** Ключи камеры, панелей,
   темы, открытого листа и прочитанных событий включают `roomId`.
10. **Модель доступа игроков (открытый вопрос).** Сейчас доступ = код комнаты +
    имя; это всё ещё слабая модель. Инвайты/PIN на игрока — возможное развитие,
    но не часть этапа 4.
11. **Архив и удаление (решено).** Архив сохраняет данные и запись каталога.
    `rooms:delete` удаляет комнату, но сначала создаёт финальную копию и
    переносит все backups в `data/deleted-rooms/`; удаление активной или
    отключённой комнаты требует `--force`. Листы другой системы по-прежнему
    скрыты без отдельного read-only хранилища.
12. **Совместимость старых backup (решено).** Манифест v1 не содержит `roomId`
    и системы, поэтому restore требует явную целевую комнату и проверяет
    системную пару, не перезаписывая чужую комнату.
13. **Полное восстановление установки (открытый процесс).** Копия создаётся и
    проверяется автоматически, но restore каталога и всех комнат остаётся
    ручной согласованной операцией при остановленном сервере.
14. **Визуальная регрессия (открытый процесс).** Автотесты и CDP проверяют
    логику, но вёрстку, перетаскивание панелей и Konva нужно периодически
    смотреть глазами в обычном браузере.
