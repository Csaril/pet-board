# Многокомнатная архитектура Tabletop Board

Статус документа: **проект, не реализовано** в части нескольких комнат. Реализованы
подготовительные этапы 1–3: боевая карта как возможность Nechronica, однократное
закрепление игровой системы за существующей единственной комнатой и изоляция данных
комнаты в `data/rooms/default/`. Многокомнатное хранение, каталог комнат, CLI комнат
и отложенная загрузка модулей остаются проектом.

Документ фиксирует текущее состояние, аудит загрузки системных модулей, сравнение
вариантов хранения и поэтапный план перехода. Он не описывает уже существующую
функциональность как готовую.

---

## 1. Текущее состояние (по коду, не по документации)

- Один процесс Fastify обслуживает одну комнату.
- Параметры комнаты берутся из `.env`: `ROOM_NAME`, `ROOM_CODE`, `GM_PASSWORD`.
- `AppConfig` содержит `roomName`, `roomCode`, `gmPassword`; аутентификация сравнивает
  введённые значения с конфигом.
- `RoomStore` получает **каталог конкретной комнаты**; в текущей сборке это
  `data/rooms/default/`, а глобальный `APP_DATA_DIR` остаётся корнем приложения.
  База лежит в `<roomDir>/room.sqlite`, ресурсы — в `<roomDir>/assets`, копии — в
  `<roomDir>/backups`. Постоянный ID `default` записан в `data/storage.json`.
- Старая раскладка `data/room.sqlite` + `data/assets` + `data/backups` не
  открывается сервером: требуется однократная команда `npm run room:migrate`.
- Кука `tb_session` содержит непрозрачный токен, сервер хранит только его SHA-256
  (`sessionDigest`) в таблице `sessions`.
- Участник и сессия разделены: `participants(id, name, role)` — стабильная
  сущность, `sessions(id, participant_id, expires_at)` — браузерный вход. На
  `participants.id` ссылаются `character_sheets.assigned_player_id`,
  `notes.owner_id`, `asset_uploaders.participant_id`, `dice_rolls.author_id/actor_id`.
  Один участник может иметь несколько сессий; старые `sessions.id` сохранены как
  `participants.id`.
- Система комнаты закрепляется один раз. Новые поля `room.system_id`,
  `room.system_version`, `room.module_config_json`, `room.system_fixed` заменяют
  изменяемую пару `active_system_id/version`. Одноразовая команда —
  `room:system:initialize` (WS) или `PUT /api/room/system` (HTTP); устаревшая
  `room:system:set` всегда отклоняется с `409 ROOM_SYSTEM_IMMUTABLE`.
- `system_fixed = 0` означает «система ещё не выбрана»; `system_fixed = 1` при
  `system_id IS NULL` — намеренный режим «без системы». Формат листов при выборе
  не мигрирует, листы другой системы скрываются из обычных API.
- `dice_rolls.system_id/system_version` фиксируют серверную атрибуцию новых
  системных событий; свободные броски остаются `NULL/NULL`. Старые
  `pbta`/`ability-use` записи получают `pbta-2d6` без выдуманной версии и
  показываются как исторические.

### Таблицы `room.sqlite`

| Таблица | Назначение | Ключевые связи |
| --- | --- | --- |
| `room` | единственная строка `id = 1`: имя, фон, сцена, закреплённая система | — |
| `sessions` | браузерные сессии | `participant_id` (`CASCADE`), `expires_at` |
| `participants` | стабильные участники комнаты | `name`, `role` |
| `dice_rolls` | последние 10 бросков (общая история) | `author_id`, `actor_id`, `character_id`, `ability_*`, `system_id/version` |
| `board_layers` | слои основной доски и боя | `scene` |
| `assets` | библиотека изображений | `UNIQUE(sha256, mime_type)` |
| `board_objects` | объекты на слоях | `asset_id`, `layer_id` (`RESTRICT`) |
| `notes` | заметки и метки | `marker_asset_id`, `owner_id` |
| `note_assets` | вложения заметок | `note_id`, `asset_id` |
| `note_markers` | метки заметок на слоях | `note_id` (`CASCADE`), `layer_id` |
| `stickers` | текстовые стикеры | `layer_id` |
| `asset_uploaders` | кто загрузил ресурс | `asset_id`, `participant_id` |
| `character_sheets` | листы персонажей | `system_id`, `system_version`, `portrait_asset_id`, `assigned_player_id` |
| `character_counters` | счётчики листа | `sheet_id` (`CASCADE`) |
| `character_abilities` | способности листа | `sheet_id` (`CASCADE`), `asset_id` |

Миграции схемы выполняются императивно в конструкторе `RoomStore` (`ALTER TABLE`,
пересоздание таблиц). Отдельной таблицы версии схемы нет.

### Существующий backup/restore

`server/backup-lib.ts` копирует `room.sqlite` и `assets/` в `<roomDir>/backups/<name>`,
манифест `version: 1` содержит имя комнаты и счётчики. Restore заменяет файлы в
`<roomDir>`. Старые копии в формате `version: 1` остаются совместимыми и после
миграции лежат в `data/rooms/default/backups/`.

## 2. Аудит загрузки System Modules

### Что загружается сейчас

- `src/modules/registry.ts` статически импортирует `pbtaSystemModule` и
  `nechronicaSystemModule`.
- `src/client/app.ts` импортирует реестр и модуль PbtA; серверные `store.ts`,
  `sheets.ts`, `index.ts` импортируют PbtA напрямую.
- Динамических `import()` нет. Отдельных чанков для систем нет.
- Метаданные обеих систем доступны до входа в комнату. Код PbtA (схема листа,
  расчёт броска, подписи характеристик) и descriptor Nechronica попадают в
  начальный JS-чанк.

### Измерения

- Начальный JS: **292 601 байт** (~286 КиБ), gzip — **84 650 байт** (~82,7 КиБ).
- Konva (minified) — ~193 КБ, то есть основная часть бандла.
- Исходники систем: `pbta-2d6/module.ts` — 1 996 Б, `roll.ts` — 2 936 Б,
  `nechronica/module.ts` — 492 Б, `registry.ts` — 967 Б; всего ~6,4 КБ.
- В собранном чанке присутствуют строки обеих систем (`Могущество`,
  `Некорректный бонус характеристики`, `Nechronica`, `Сила Судьбы`).
- Точный вклад каждого модуля без bundle analyzer не измерялся. По исходникам
  вклад Nechronica сейчас меньше 1 КБ; вклад PbtA — несколько КБ. Выигрыш от
  разделения бандла сегодня небольшой, но архитектурно важен для будущих систем.

### Что выполняется/загружается лишнего

- Код обеих систем парсится и выполняется при старте.
- Данные листов не грузятся до входа, но клиент запрашивает листы закреплённой
  системы после входа; сервер уже фильтрует их по `room.system_id/version`.
- История бросков не фильтруется по системе: `getDiceRolls()` возвращает
  последние 10 записей комнаты независимо от `kind`/системы. Записи без
  совпадающей системной атрибуции остаются видимыми как «Историческая запись»,
  не запускают механику и не могут быть повторены.
- Ресурсы грузятся по требованию (по ID), но каталог ресурсов и данные комнаты
  не разделены между комнатами, потому что комната одна.

## 3. Сравнение вариантов хранения

### A. Отдельная SQLite на комнату + `catalog.sqlite`

Плюсы:
- Изоляция на уровне файла: забытый `WHERE room_id = ?` не может отдать чужие данные.
- `RoomStore` уже принимает каталог комнаты (`roomDir`); достаточно передать ему каталог другой комнаты.
- Backup/restore, удаление и перенос комнаты — операции над каталогом.
- Ресурсы и резервные копии лежат рядом с БД комнаты.
- Падение/повреждение одной БД не блокирует остальные комнаты.
- Схемные миграции можно запускать при открытии конкретной комнаты.

Минусы:
- Несколько открытых соединений `better-sqlite3`; нужен пул/LRU и закрытие простаивающих.
- Административные запросы «по всем комнатам» идут через каталог и обход комнат.
- Общая дедупликация ресурсов между комнатами сложнее (в v1 не нужна).

### B. Одна SQLite с `room_id` во всех таблицах

Плюсы:
- Одно соединение, проще глобальные отчёты и общий backup.
- Одна миграция схемы на весь сервер.

Минусы:
- Каждый из десятков запросов `RoomStore` обязан фильтровать `room_id`; любая
  забытая фильтрация — утечка листов, заметок, истории бросков или ресурсов.
- Составные внешние ключи (`room_id, id`) и индексы во всех таблицах.
- Восстановление одной комнаты из общей БД — выборочная операция, а не замена файла.
- Удаление комнаты требует каскадной очистки и проверки ссылок на ресурсы.
- Текущий `RoomStore` придётся переписать почти целиком, риск регрессий выше.

### Рекомендация

**Вариант A**: `data/catalog.sqlite` + `data/rooms/<room-id>/room.sqlite`,
`assets/`, `backups/`. Он лучше соответствует текущему коду, даёт сильную изоляцию
и позволяет сохранить существующие backup/restore и `RoomStore` с минимальными
изменениями. Глобальную дедупликацию ресурсов не вводить в первой версии.

Этап 3 реализовал левую часть схемы без каталога: единственная комната имеет
постоянный ID `default`, который хранится в `data/storage.json`. Каталог комнат
сможет сослаться на этот же ID и каталог без повторного переноса базы.

## 4. Рекомендуемая архитектура

### 4.1 Каталог

`data/catalog.sqlite`:

```sql
CREATE TABLE rooms (
  id TEXT PRIMARY KEY,                 -- UUID, не меняется
  name TEXT NOT NULL,
  system_id TEXT,                      -- NULL допустим только в режиме «без системы»
  system_version TEXT,
  system_fixed INTEGER NOT NULL DEFAULT 0 CHECK (system_fixed IN (0, 1)),
  room_code_hmac TEXT NOT NULL UNIQUE, -- HMAC(нормализованный код, server pepper)
  gm_password_hash TEXT NOT NULL,      -- scrypt/argon2id + соль
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'disabled')),
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

- Код комнаты не хранится открытым: для поиска используется HMAC с секретом
  сервера (`data/server-secret`, права `0600`). Короткий код нельзя безопасно
  хранить обычным хешем — он перебирается офлайн.
- Пароль GM — медленный KDF (scrypt) с индивидуальной солью, сравнение
  constant-time.
- `system_id`/`system_version`/`system_fixed` в каталоге дублируются в
  `room.sqlite` и защищаются триггером от изменения. Выбор делается один раз:
  `system_fixed = 0` — ещё не выбрано, `system_fixed = 1` + `NULL/NULL` —
  намеренный режим без системы.

### 4.2 Комната

`data/rooms/default/room.sqlite` — все игровые данные. Изоляция каталога и
разделение участников уже выполнены в единственной комнате:

- `participants(id, name, role, created_at)` и
  `sessions(id, participant_id REFERENCES participants(id) ON DELETE CASCADE,
  expires_at, created_at)`. Старые ID участников сохранены при миграции.
- `room.system_id`, `room.system_version`, `room.module_config_json`,
  `room.system_fixed`; триггеры `room_system_immutable`,
  `room_system_fixed_immutable`, `room_legacy_system_immutable`,
  `room_system_pair_update` запрещают обычную смену закреплённой пары.
- `dice_rolls.system_id`, `dice_rolls.system_version` с серверной атрибуцией;
  исторические записи не получают выдуманную версию.
- `character_sheets` с `system_id/system_version/schema_version`; листы другой
  системы сохраняются, но скрываются из обычных API.

Остаётся добавить при переходе на несколько комнат:

- `room_schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT)`.
- `rooms/<id>/room-config.json` с кодом/именем/секретом комнаты вместо `.env`.
- `payload_json` для листов только если понадобится формат, не выражаемый
  текущими колонками.

### 4.3 Маршрутизация и сессии

- `POST /api/session` принимает `roomCode`, имя, роль и пароль GM. Сервер находит
  комнату по HMAC кода в каталоге, проверяет пароль, открывает `RoomStore`.
- Кука `tb_session` = `<roomId>.<token>`; сервер проверяет HMAC-токен и
  принадлежность комнате. Все существующие эндпоинты сохраняют пути; комната
  определяется по куке, а не по URL.
- WebSocket `/ws` резолвит комнату по куке; сокеты группируются по
  `roomId + sessionId`, рассылка `room:state` идёт только участникам комнаты.
- Переключение комнаты = новый вход; клиент сбрасывает локальное состояние,
  ключи `localStorage` включают `roomId` (камера, панели, счётчики).

### 4.4 Управление комнатами

Рекомендуется **CLI**, без веб-админки на первом этапе:

```text
npm run rooms -- create --name "..." --system pbta-2d6 --system-version 1.0.0 \
  --code <code> --gm-password-stdin
npm run rooms -- list
npm run rooms -- disable <room-id>
npm run rooms -- delete <room-id> --force
npm run rooms -- import-legacy --source ./data --room <room-id>
npm run rooms -- sheets archive --room <room-id> --system nechronica
```

CLI работает с теми же модулями каталога/хранилища, что и сервер, не требует
перезапуска и не печатает секреты в лог. Веб-интерфейс можно добавить позже,
когда появятся роли администратора и аудит действий.

### 4.5 Изоляция данных

- Каждый ресурс принадлежит комнате: файл лежит в `rooms/<id>/assets/<asset-id>`.
- Выдача файла: сначала проверка строки `assets` в БД **этой** комнаты, затем
  чтение файла. Знание ID чужого ресурса бесполезно.
- Удаление проверяет ссылки (`board_objects`, `notes`, `note_assets`,
  `character_sheets`, `character_abilities`) в пределах комнаты.
- Дедупликация SHA-256 — внутри комнаты (`UNIQUE(sha256, mime_type)` уже это даёт).
- Листы фильтруются по комнате (файл БД) и по `system_id/system_version`.
- История бросков и WebSocket-рассылка — только в пределах комнаты.
- Сессии привязаны к комнате; чужой `roomId` в куке не даёт доступа.

### 4.6 Отложенная загрузка модулей

- В ядре — только метаданные: `{ id, version, name, capabilities }`.
- Клиент: явная карта загрузчиков, без интерполяции пользовательских строк:
  `() => import('./system/pbta-2d6/client.js')`. Загрузка после получения
  `room:state` с `systemId/systemVersion`; кэш `Promise` по `id@version`;
  `mount/dispose` при смене комнаты.
- Сервер: такая же явная карта `() => import('./system/.../server.js')`;
  загрузка по ID из каталога, кэш на процесс. Node кэширует ES-модули, поэтому
  выгрузки из памяти не обещаем; один экземпляр кода обслуживает все комнаты
  одной версии.
- Модуль не хранит состояние комнаты в module-level переменных: конфиг, store и
  identity передаются аргументами.
- Точная версия обязательна. Если комната закреплена за версией, которой нет в
  сборке, сервер отказывается открывать комнату (или требует явную миграцию).
  Каталоги версий: `system/pbta-2d6/1.0.0/`.
- Обновление модуля: новая комната получает новую версию; существующая —
  только через `rooms migrate-system` с резервной копией и зарегистрированными
  миграциями `sheet_schema_version`.

## 5. План перехода

### Этап 1. Боевая карта (выполнено)

- Причина: на узкой ширине группа «Боевая карта» переносится в меню «Ещё».
  `toggleMenu` вызывал `closeMenus()`, который скрывал родительское меню, а
  вложенное меню оставалось внутри `display: none`.
- Исправление: `menuIsWithin()` в `src/shared/menu.ts`; `closeMenus(keep?)`
  сохраняет открываемое меню и его предков; `toggleMenu` передаёт `menu`.
- Тест: сценарий 29 в `server/ux.test.ts`; ручная проверка на 900 и 1400 px.
- Затрагиваемые файлы: `src/shared/menu.ts`, `src/client/app.ts`, `server/ux.test.ts`.
- БД/API/WebSocket не менялись.

### Этап 2. Закрепление системы за комнатой (выполнено)

Файлы: `server/store.ts`, `server/index.ts`, `server/sheets.ts`,
`server/board.ts`, `src/client/app.ts`, `src/pages/index.astro`,
`src/shared/board.ts`, `src/styles/global.css`, `server/system.test.ts` и
существующие тесты.

- БД: `room.system_id`, `room.system_version`, `room.module_config_json`,
  `room.system_fixed`; миграция из `active_system_id/version` только при полной
  известной паре; триггеры неизменяемости и парной целостности.
- API/WS: `room:system:initialize` и `PUT /api/room/system` выполняют выбор один
  раз; `room:system:set` всегда возвращает `409 ROOM_SYSTEM_IMMUTABLE`;
  системные несовпадения — `409 SYSTEM_MISMATCH`.
- UI: селектор показывается только до фиксации; после неё — read-only название и
  версия. Смена системы через интерфейс невозможна.
- Данные: листы другой системы сохраняются, но скрываются из снимка, списков,
  HTTP API и редактирования. Новые системные броски и способности получают
  `system_id/version` от сервера; свободные броски — `NULL/NULL`; исторические
  записи помечаются и не запускают механику.
- Тесты: миграция копии реальной базы, идемпотентность, сохранение ID, режим
  «без системы», триггеры, отказы HTTP/WS, изоляция листов/истории и
  backup/restore. Ручная проверка комнат Nechronica/PbtA и двух браузеров
  остаётся финальным чек-листом.
- Готово: `systemId/version` нельзя изменить ни командой, ни обычным UPDATE;
  данные и ID сохраняются.

### Этап 3. Изоляция данных комнаты (выполнено)

Файлы: `server/room-storage.ts` (новый), `server/room-migrate.ts` (новый),
`server/store.ts`, `server/assets.ts`, `server/index.ts`, `server/auth.ts`,
`server/backup-lib.ts`, `server/backup.ts`, `server/sheets.ts`,
`src/modules/registry.ts`, `src/modules/system/*/module.ts`, `src/shared/board.ts`,
`src/client/app.ts`, `package.json` и тесты.

- БД: `participants`, `sessions.participant_id`; старые `sessions.id` стали
  `participants.id`. Один участник может иметь несколько сессий.
- Хранилище: `data/rooms/default/{room.sqlite,assets,backups}`; постоянный ID
  `default` и версия раскладки — в `data/storage.json`. `APP_DATA_DIR` остаётся
  корнем. Сервер отказывается стартовать со старой раскладкой.
- Миграция: `npm run room:migrate` при остановленном сервере. Создаёт полную
  копию `data/`, переносит БД через SQLite backup API, копирует assets и backups,
  проверяет `integrity_check`, `foreign_key_check`, количество строк, размеры и
  SHA-256, открывает `RoomStore` и создаёт проверочную копию. Маркер пишется
  последним; старые файлы не удаляются. Повторный запуск идемпотентен.
- Ресурсы: `RoomStore.assetsDir` и `RoomStore.backupsDir` принадлежат экземпляру;
  SHA-256-дедупликация и проверка ссылок — в пределах комнаты.
- WS: соединения по-прежнему ключуются `sessionId`, но рассылка и `participants`
  дедуплицируются по `participantId`; закрытие одной сессии не затрагивает другие.
- Боевая карта: `capabilities.battleMap` в `SystemModuleDescriptor`; Nechronica —
  `true`, PbtA — `false`. Сервер проверяет capability через `RoomStore`, а не
  доверяет клиентскому `systemId`/полям команды. Старая PbtA-сцена `battle`
  переводится на `board` при открытии, данные сцены сохраняются.
- Не реализовано намеренно: `catalog.sqlite`, CLI комнат, многокомнатная cookie-
  модель и авторизация, LRU, динамическая загрузка модулей, перенос листов между
  комнатами. `ROOM_CODE`, `GM_PASSWORD`, `ROOM_NAME` остаются в `.env`.
- Тесты: `server/room-store.test.ts`, `server/participants.test.ts`,
  `server/room-storage.test.ts`, `server/battle-capability.test.ts` и обновлённые
  регрессионные наборы.
- Готово для следующего этапа: можно создать второй `RoomStore` с другим каталогом
  без изменения глобальных настроек; маршрутизация нескольких комнат ещё не
  реализована.

### Этап 4. Несколько комнат на одном сервере

Файлы: `server/catalog.ts` (новый), `server/config.ts`, `server/index.ts`,

## 6. Перенос старых данных

1. Остановить сервер. Сделать `npm run backup` и дополнительно скопировать
   весь `data/` вручную.
2. Создать комнату: `rooms create --name ... --system <id> --system-version <v>
   --code ... --gm-password-stdin`. Получить `<room-id>`.
3. `rooms import-legacy --source ./data --room <room-id>`:
   - скопировать `room.sqlite` в `data/rooms/<room-id>/room.sqlite`;
   - скопировать `assets/*` в `data/rooms/<room-id>/assets/`, пропуская файлы с
     совпадающим SHA-256; проверить, что каждый `assets.id` имеет файл;
   - перенести `room.name`; записать `system_id/system_version` из
     `active_system_id/version` (или из явного `--system`, если не задана);
   - создать `participants` из `sessions.id`, сохранив те же ID, чтобы
     `assigned_player_id`, `owner_id`, `asset_uploaders.participant_id` и
     `dice_rolls.author_id` продолжали ссылаться на существующие записи;
   - старые сессии оставить рабочими на время перехода: legacy-кука без
     `roomId` привязывается к единственной мигрированной комнате; после
     повторного входа кука получает `roomId`;
   - историю бросков сохранить как есть (последние 10; ограничение существующее);
   - листы других систем **не удалять**. После этапа 2 они уже сохраняются в
     комнате, но скрыты из API/UI и не редактируются. При переносе в
     многокомнатное хранилище можно оставить их в основной таблице (текущее
     поведение) или вынести в отдельный архив; решение принимается на этапе 6.
4. Проверки: `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, сравнение
   количества строк по таблицам, количества файлов и хэшей, выборочное открытие
   листов, заметок, меток и боевой карты.
5. Переключить каталог на новую комнату. Старый `data/` не удалять до успешной
   проверки. Откат — вернуть старый `APP_DATA_DIR` и перезапустить.

### Судьба листов нескольких систем

- Не удалять и не «исправлять» автоматически.
- На этапе 2 листы другой системы остаются в `character_sheets`, но скрыты из
  обычных API и не редактируются; архивы комнат не реализованы.
- Если GM хочет продолжить игру в другой системе — создать отдельную комнату и
  при необходимости импортировать туда листы отдельной командой.
- Архив как отдельное хранилище и read-only экспорт — возможное расширение
  этапа 6, а не текущая функциональность.

## 7. Риски и открытые вопросы

1. **ID сессии больше не равен ID участника (решено на этапе 3).** Старые
   `sessions.id` перенесены в `participants.id`, поэтому назначения листов,
   заметки и загрузчики сохранили ссылки. При дальнейших миграциях нельзя
   пересоздавать participant ID; новые сессии получают собственные ID.
2. **Короткий код комнаты.** Нужен HMAC с секретом сервера и rate limit;
   обычный хеш перебирается. Смена кода должна быть явной операцией.
3. **Секреты в `.env`.** После перехода `.env` не должен содержать комнатных
   секретов; нужен `.env.example` без них и инструкция по CLI.
4. **`better-sqlite3` синхронный.** Много комнат = много соединений и памяти.
   Нужен LRU/закрытие простаивающих; при росте нагрузки — отдельные процессы.
5. **Кэш ES-модулей.** Код системы нельзя выгрузить; принимаем один экземпляр
   на версию и требуем отсутствия состояния в модуле.
6. **Точные версии модулей.** Если старая версия удалена из сборки, комната не
   откроется. Нужна политика хранения версий или обязательная миграция.
7. **Backup во время записи.** Копирование файла БД на работающем сервере может
   дать несогласованный снимок; нужен SQLite backup API или остановка записи.
8. **Ресурсы и дедупликация.** В v1 — только внутри комнаты. Глобальная
   дедупликация потребует отдельного реестра ссылок и усложнит удаление.
9. **Локальное состояние браузера.** Камера, панели, счётчики и выбранные листы
   должны быть привязаны к `roomId`, иначе после смены комнаты останутся чужие
   настройки.
10. **Модель доступа игроков.** Сейчас доступ = код комнаты + имя; после
    разделения комнат это всё ещё слабая модель. Стоит рассмотреть инвайты/PIN
    на игрока, но это отдельное решение.
11. **Продуктовое решение по архиву.** Этап 2 выбрал скрытие листов другой
    системы без архива. При появлении нескольких комнат нужно подтвердить,
    останется ли это поведение или архивные листы будут вынесены в отдельное
    read-only хранилище.
12. **Совместимость старых backup.** Манифест v1 не содержит `roomId` и системы;
    restore должен явно спрашивать целевую комнату и не перезаписывать чужую.
