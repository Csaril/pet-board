# Tabletop Board

Локальная совместная доска для НРИ. Проект развивается по этапам из [технического задания](./NRI_Board_TZ_Codex.md). Сейчас реализован только Этап 1: постоянная комната, вход ведущего и игроков, сохранение сессий и подключение через WebSocket.

## Совместимость

- Node.js 24 LTS, 64-bit Intel macOS и Apple Silicon. Версия проекта закреплена в `.nvmrc`.
- Проверено в окружении: macOS 15.7.9, Node.js 24.5.0 (x64 совместимая ветка), npm 11.5.1.
- Для MacBook Pro 13-inch (2018, Intel) используйте последнюю исправленную версию Node 24 LTS. Установленная `24.5.0` подходит для разработки, но её следует обновить до актуального патча.

Node.js 24 доступен как macOS x64 и находится в LTS; см. [таблицу релизов Node.js](https://nodejs.org/en/about/previous-releases) и [официальный архив Node 24](https://nodejs.org/en/download/archive/v24). Не используйте Current/экспериментальные версии для запуска сервера.

## Архитектура

Один процесс Fastify обслуживает HTTP API, WebSocket и статическую сборку Astro на одном порту. Astro компилирует frontend в `dist/`; сервер Node.js и общая логика TypeScript находятся отдельно. Состояние комнаты и хэши сессий сохраняются в локальной SQLite-базе. Данные игры не отправляются во внешнее облако.

```text
src/
  pages/                 Astro-страницы
  styles/                стили интерфейса
  shared/                общие типы для клиента и сервера
server/
  index.ts               Fastify, HTTP API и WebSocket
  auth.ts                проверка кодов и создание сессий
  config.ts              конфигурация окружения
  store.ts               SQLite и срок действия сессий
  backup.ts              резервная копия базы
  *.test.ts              проверки Этапа 1
data/
  room.sqlite            постоянная комната и сессии (не добавлять в Git)
  backups/               резервные копии базы
```

Данные комнаты на Этапе 1: имя комнаты и записи сессий (случайный токен хранится в браузерной cookie, в SQLite лежит его SHA-256-хэш, имя, роль и срок действия). После перезапуска сервера действующая браузерная сессия восстанавливается. Сервер допускает одну GM-сессию; игроки могут входить независимо.

## Зависимости

- `astro` — статическая сборка интерфейса.
- `fastify` и официальные плагины `@fastify/static`, `@fastify/websocket`, `@fastify/cookie`, `@fastify/rate-limit` — один HTTP/WebSocket-сервер, cookie и ограничение попыток входа.
- `better-sqlite3` — локальное постоянное хранилище.
- `dotenv` — загрузка локального `.env`.
- Dev-зависимости: TypeScript, Astro checker, `tsx` и `ws` для типизированных HTTP/WebSocket-тестов.

React/Vue, UI-библиотека, отдельный WebSocket-сервер и облачная база на этом этапе не нужны. Konva, загрузка изображений, заметки, листы и игровые модули относятся к следующим этапам.

## Установка и запуск

```sh
nvm use
npm ci
cp .env.example .env
```

Замените `ROOM_CODE` и `GM_PASSWORD` длинными случайными секретами (минимум 12 символов). Например, сгенерируйте два значения командой `openssl rand -base64 24` и впишите их в `.env`. Не публикуйте этот файл и не пересылайте пароль ведущего игрокам.

Для локального запуска:

```sh
npm run dev
```

Сервер слушает `http://127.0.0.1:4321`. Перед запуском `.env` должен содержать код комнаты и пароль GM. Команда `dev` собирает Astro и перезапускает backend при изменениях в `server/`; после изменений интерфейса повторите `npm run build` и перезапустите сервер.

Production-сборка и запуск:

```sh
npm run build
NODE_ENV=production npm start
```

При `NODE_ENV=production` cookie становится `Secure`. Публичный HTTPS-доступ через ngrok относится к Этапу 6; пока не публикуйте сервер без HTTPS-туннеля и надёжных секретов. Для локальной разработки cookie не Secure, чтобы работал обычный HTTP на loopback.

## Переменные окружения

| Имя | Обязательная | По умолчанию | Назначение |
|---|---:|---|---|
| `ROOM_CODE` | Да | — | Общий код комнаты, не короче 12 символов |
| `GM_PASSWORD` | Да | — | Пароль ведущего, не короче 12 символов |
| `ROOM_NAME` | Нет | `Игровая комната` | Имя, записываемое при первом создании базы |
| `HOST` | Нет | `127.0.0.1` | Адрес привязки сервера |
| `PORT` | Нет | `4321` | Порт HTTP/API/WebSocket |
| `APP_DATA_DIR` | Нет | `./data` | Каталог локальной базы и резервных копий |
| `SESSION_DAYS` | Нет | `30` | Срок действия сессии, 1–365 дней |
| `NODE_ENV` | Нет | `development` | В production включает Secure-cookie |

## Резервная копия

Сначала выполните production-сборку, затем из каталога проекта запустите:

```sh
npm run backup
```

Команда создаёт согласованную SQLite-копию в `data/backups/`. Скопируйте её на отдельный локальный носитель; не помещайте базу или backup в публичный Git-репозиторий. Для восстановления остановите сервер и замените `data/room.sqlite` выбранной копией.

## Архитектурные решения и риски

- **Вход и приватность:** сервер принимает роль, но назначает её только после проверки кода комнаты/секрета GM. Cookie HttpOnly, SameSite=Strict и Secure в production; в SQLite хранится хэш случайного токена. API и WebSocket сверяют Origin. Ошибка входа не раскрывает, какое именно значение неверно.
- **Перебор секретов:** вход ограничен 20 запросами в минуту на сетевой адрес. При запуске через локальный ngrok-агент все запросы могут выглядеть для приложения как один адрес; это нужно учесть при настройке доверия прокси на Этапе 6, не включая бездумно доверие произвольным `X-Forwarded-For`.
- **Сохранение:** SQLite и файл данных доступны процессу ведущего; задавайте каталог с обычными правами пользователя и регулярно делайте резервную копию. База и каталог исключены из Git.
- **Синхронизация:** WebSocket серверный; клиент не сообщает свою роль в каждом сообщении. На Этапе 1 через сокет передаётся только имя комнаты, роль текущей сессии и список активных участников. Позднее каждое изменение состояния должно получать серверную авторизацию и фильтрацию по роли.
- **Ограничение этапа:** комнаты с разными кодами, доска, загрузки, права объектов, заметки и листы пока не реализованы. В проекте нет фиктивных кнопок для этих функций.

## План

1. **Этап 1 — подключение (выполнен):** структура приложения, Fastify и Astro, SQLite, GM/Player-вход, защищённые сессии, WebSocket и восстановление сессии.
2. **Этап 2:** холст, изображения, библиотека ресурсов и GM-слои.
3. **Этап 3:** стикеры, интерактивные метки и приватные заметки.
4. **Этап 4:** листы персонажей и разрешения просмотра/редактирования.
5. **Этап 5:** PbtA 2d6 как встроенный модуль.
6. **Этап 6:** эксплуатационная проверка, ngrok, backup/restore и проверка доступов.
