# Tabletop Board

Локальная совместная доска для НРИ. Реализованы Этапы 1–6 и многокомнатный этап 4: подключение ведущего и игроков, общий холст с изображениями и слоями, интерактивные заметки и текстовые стикеры, встроенный модуль PbtA, общая лента бросков и применений способностей, листы персонажей с назначением игрокам, production-запуск, резервное копирование и работа через ngrok. Верхняя панель сгруппирована и адаптируется к ширине окна, а для пользовательского текста доступен локальный шрифт Caveat.

Один Fastify-сервер обслуживает несколько независимых комнат. Комнаты обнаруживаются по коду через `data/catalog.sqlite`, каждая имеет собственный `data/rooms/<room-id>/` с SQLite, изображениями, backups и сессиями. Каждая комната навсегда закреплена за одной игровой системой: выбор делается один раз при создании или миграции базы и после этого не меняется. Nechronica зарегистрирована как независимый модуль, лист персонажа и меню бросков показываются заглушками и не используют характеристики, формулы и обработчики PbtA. Боевая карта — вторая сохранённая сцена доски с отдельными слоями, объектами, стикерами, метками и фоном; ведущий может готовить её локально и вызывать для всех участников отдельной командой.

- Проверенное окружение: macOS 15.7.9, Intel `x86_64`, Node.js 24.5.0, npm 11.5.1. Рекомендуется последний патч ветки Node 24.

## Архитектура

Один Fastify-сервер обслуживает Astro frontend, HTTP API, загрузку файлов и WebSocket-команды на одном порту. Astro собирает статический интерфейс, Konva рисует двумерный холст. Комнату, закреплённую игровую систему, участников и сессии, фон доски, последние броски, слои, объекты, заметки, размеры меток, стикеры, листы и метаданные ресурсов хранит SQLite; оригинальные изображения лежат отдельными файлами в `data/rooms/<room-id>/assets/` под случайными ID.

Pan/zoom холста хранится в localStorage конкретного браузера и не рассылается участникам. Изменения доски идут через WebSocket-команды; сервер проверяет роль, владельца стикера, назначение листа и свойства слоя, записывает изменение в SQLite и рассылает каждому участнику разрешённую проекцию. Содержимое заметок запрашивается отдельным защищённым HTTP-запросом только при локальном открытии; WebSocket передаёт метки без текста и вложений. Изображение без разрешения на перемещение для игрока остаётся видимым, но не перехватывает указатель: клик по нему начинает панорамирование камеры. Личные заметки игроков не имеют меток и координат; их список фильтруется на сервере, а текст и изображения выдаются только владельцу и ведущему. Панель заметок открывается и закрывается только локально: общие обновления комнаты и броски не меняют её видимость. Неназначенные листы персонажей и их изображения исключаются из проекции игрока. Оригинал изображения не перезаписывается при обрезке, отражении или трансформации. Смена фона меняет только CSS-фон рабочей области и не затрагивает камеру, объекты, заметки или стикеры.

### Сцены и боевая карта

Комната хранит две независимые сцены: `board` (основная доска) и `battle` (боевая карта). Сцена — это не режим видимости: у каждой сцены собственные слои, объекты, стикеры, метки и фон. Связь задаётся через `board_layers.scene`, а объекты, стикеры и метки наследуют сцену своего слоя. Одна комната содержит ровно одну боевую карту.

Боевая карта — не общая функция ядра, а возможность системного модуля. В `SystemModuleDescriptor` есть типизированное поле `capabilities.battleMap`: у Nechronica оно `true`, у PbtA — `false`. Снимок комнаты отдаёт `system.capabilities`, поэтому интерфейс PbtA не создаёт группу «Боевая карта», кнопки и предпросмотр. Сервер проверяет возможность через закреплённую систему и доверенный реестр модулей; клиентские `systemId` или `capabilities` в команде не учитываются. Если старая PbtA-база содержала `active_scene = 'battle'`, комната открывается на `board`, а данные боевой сцены и её объекты сохраняются.

- `room.active_scene` — сцена, которую видят все участники. Меняется только ведущим командой `room:scene:set`.
- `room.battle_background` — фон боевой карты; основная доска продолжает использовать существующее поле `room.background`.
- `board_layers.scene` — `board` или `battle`; индекс `board_layers_scene_order(scene, order_index)` ускоряет выборку слоёв сцены.
- Миграции аддитивные: существующие базы получают `active_scene = 'board'`, `battle_background = 'gray'` и `scene = 'board'` для старых слоёв; затем создаются недостающие слои обеих сцен. Значения по умолчанию сохраняют прежнее поведение основной доски.

Снимок комнаты (`room:state` и `GET /api/board`) содержит `activeScene` и данные активной сцены в прежних полях (`background`, `layers`, `objects`, `stickers`, `noteMarkers`). Ведущему дополнительно передаётся объект `battle` с содержимым боевой карты — для локального предпросмотра без переключения игроков — только если закреплённая система объявляет `capabilities.battleMap`. Игрок поле `battle` не получает и видит только активную сцену.

Команды слоёв, объектов, меток, стикеров и `room:background:set` принимают необязательное поле `scene`. Игрок может менять только активную сцену; ведущий — любую. Без поля команда применяется к активной сцене. Камера (pan/zoom) и активный слой хранятся в localStorage отдельно для каждой сцены; сервер их не синхронизирует. После переподключения участник получает актуальную активную сцену и восстанавливает её локальную камеру.

Предпросмотр боевой карты ведущим — локальное состояние браузера (`viewingBattle`): холст показывает боевую карту, команды явно передают `scene: 'battle'`, но игроки остаются на активной сцене. Кнопка «Вызвать боевую карту» отправляет глобальную команду `room:scene:set`; «Вернуться на основную доску» возвращает `board`. Обе доступны только ведущему в комнате с поддержкой боевой карты; сервер повторно проверяет роль и capability. В PbtA команды `room:scene:set` и `room:background:set` со сценой `battle` отклоняются с `409 SYSTEM_MISMATCH`.

Удаление ресурса учитывает все ссылки, включая объекты, вложения заметок, портреты и изображения способностей на боевой карте. Backup/restore сохраняют `active_scene`, `battle_background`, закреплённую систему, слои и объекты обеих сцен вместе с изображениями.

### Система комнаты

Игровая система выбирается один раз и навсегда закрепляется за комнатой. Новая база начинает с `system_fixed = 0`; ведущий может один раз выполнить `room:system:initialize` (WebSocket) или `PUT /api/room/system` (HTTP). Повторная попытка, а также устаревшая команда `room:system:set` получают `409 Conflict` с кодом `ROOM_SYSTEM_IMMUTABLE`. Несовпадение системной механики или листа даёт `409` с кодом `SYSTEM_MISMATCH`.

- `room.system_id`, `room.system_version` — закреплённая пара модуля; `room.module_config_json` — конфигурация выбранного модуля; `room.system_fixed` — признак завершённого выбора.
- `system_fixed = 0` — система ещё не выбрана. `system_fixed = 1` при `system_id IS NULL` — намеренный режим «без системы»: доска, заметки, стикеры и свободные броски работают, системные листы и механики — нет.
- Снимок комнаты содержит `system: { fixed, id, version, name, config, capabilities }`. Селектор показывается только при `fixed = false`; после фиксации интерфейс показывает систему только для чтения.
- SQLite-триггеры `room_system_immutable`, `room_system_fixed_immutable`, `room_legacy_system_immutable` и `room_system_pair_update` запрещают обычное изменение закреплённых полей и частичную пару ID/версии. Будущая контролируемая миграция версии должна явно снять триггер в собственной транзакции.
- Миграция старой базы переносит `active_system_id`/`active_system_version` в новую пару только когда заданы оба поля и модуль известен; иначе запуск завершается понятной ошибкой без фиксации системы. Если оба старых поля `NULL`, выбор остаётся за ведущим.
- Листы других систем не удаляются и не преобразуются, но скрываются из `room:state`, `GET /api/sheets`, `GET /api/sheets/:id`, обычных списков и не редактируются.
- Новые системные броски и применения способностей получают `system_id`/`system_version` только от сервера. Свободные броски хранятся с `NULL/NULL`. Старые записи классифицируются только при однозначном типе: `pbta`/`ability-use` → `pbta-2d6` без выдуманной версии, `free` → `NULL/NULL`. Такие записи показываются как «Историческая запись», не запускают механику и не могут быть повторены через текущую систему.

### Комнаты, каталог и авторизация

Сервер обслуживает несколько независимых комнат. Каталог `data/catalog.sqlite` содержит только метаданные поиска и авторизации, а игровые данные каждой комнаты остаются в её собственном каталоге:

```text
data/
  catalog.sqlite               # комнаты, HMAC-коды, scrypt-хэши GM-паролей, статусы
  server-secret                # HMAC-секрет каталога, 32+ байта, права 0600
  catalog-backups/             # копии каталога и полной установки
  storage.json                 # version: 1, roomId: "default", layout: "rooms"
  rooms/default/               # перенесённая существующая комната
    room.sqlite
    assets/
    backups/
  rooms/<room-id>/             # новая независимая комната
    room.sqlite
    assets/
    backups/
```

`APP_DATA_DIR` остаётся корнем приложения. ID комнаты — стабильная случайная строка (UUID для новых комнат), а не имя: имя можно менять, каталог от него не зависит. `RoomStore` получает явный каталог комнаты и хранит собственные `roomDir`, `assetsDir` и `backupsDir`; глобального «текущего» хранилища нет.

Таблица каталога:

```sql
CREATE TABLE rooms (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  system_id TEXT,
  system_version TEXT,
  room_code_hmac TEXT NOT NULL UNIQUE,
  gm_password_hash TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'disabled', 'archived')),
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

- Код комнаты не хранится открытым: в каталоге только `HMAC-SHA256` с секретом `server-secret`. Новый код — 8 символов из `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`. Короткие коды сравниваются без учёта регистра и с обрезкой пробелов; старые длинные коды сохраняют регистр.
- `server-secret` создаётся только при инициализации каталога, имеет права `0600` и не перегенерируется. Если `catalog.sqlite` уже существует, а секрет отсутствует или повреждён, сервер завершается с понятной ошибкой: новый секрет сделал бы все коды недействительными.
- Пароль ведущего хранится как `scrypt`-хэш с индивидуальной солью и проверяется constant-time. Открытый пароль не попадает в каталог, логи, CLI-вывод и клиент.
- Статусы: `active` — комната работает; `disabled` — вход и HTTP/WS отклоняются; `archived` — данные и запись сохранены, финальная копия создана, включение запрещено. `rooms:delete` физически удаляет каталог комнаты и запись каталога; по умолчанию сначала создаётся финальная копия, а все backups переносятся в `data/deleted-rooms/`.
- Статус читается из каталога на каждом запросе и сообщении. Работающий сервер замечает изменения CLI без перезапуска; WebSocket-соединения отключённой или архивированной комнаты закрываются в течение пары секунд.
- `RoomManager` открывает `room.sqlite` лениво, при первом обращении. Одновременно открыто не более `MAX_OPEN_ROOMS` комнат (по умолчанию 8). Каждый HTTP-запрос и WebSocket-соединение держит lease; LRU закрывает только комнаты без активных lease. При переполнении возвращается понятная ошибка, а не безлимитное открытие баз.
- Перед открытием проверяются `system_id`/`system_version` каталога и `room.sqlite`, а также отсутствие path traversal. Комната с незафиксированной или противоречащей каталогу системой не открывается.

Участник и браузерная сессия разделены и принадлежат комнате:

- `participants(id, name, role, created_at)` — стабильный участник комнаты.
- `sessions(id, participant_id, expires_at, created_at)` — вход в браузере; у одного участника может быть несколько сессий, закрытие одной не затрагивает другие.
- Старые `sessions.id` при миграции становятся `participants.id`, поэтому листы, заметки, загрузки и история сохраняют прежние ссылки.
- Повторный вход с тем же именем и ролью переиспользует участника; новый браузер получает отдельную сессию.
- Код комнаты определяет, в какой `RoomStore` войдёт клиент. Пароль проверяется только для роли GM и только у выбранной комнаты.
- После входа клиент переходит на `/room/<room-id>`. Cookie называется `tb_session_<roomId>`, имеет `HttpOnly`, `SameSite=Strict`, `Path=/`, а `Secure` включается при фактическом HTTPS. Выход из одной комнаты удаляет только её cookie; сессии других комнат в том же браузере продолжают работать.
- Один браузер может держать несколько комнат в разных вкладках. Камера, zoom, открытые панели, открытый лист, прочитанные события, тема и другие локальные настройки хранятся в `localStorage` с префиксом комнаты и не пересекаются между вкладками разных комнат.
- Ошибка входа нейтральна и не перечисляет существующие комнаты; попытки входа ограничены rate limit.

### Миграция существующей комнаты `default`

Старая раскладка `data/room.sqlite` + `data/assets` + `data/backups` сначала переносится командой `npm run room:migrate` при остановленном сервере. Затем существующая `data/rooms/default/` регистрируется в каталоге:

```sh
npm run build
npm run rooms:init
```

`rooms:init` идемпотентен: он читает `ROOM_NAME`, `ROOM_CODE` и `GM_PASSWORD` из `.env`, создаёт `catalog.sqlite` и `server-secret`, регистрирует `default` с её текущей закреплённой системой и переносит код/пароль в защищённое хранилище. Повторный запуск не меняет код, пароль, имя или систему и не печатает секреты. `.env` автоматически не переписывается.

После успешной инициализации обычный сервер больше не требует `ROOM_CODE`, `GM_PASSWORD` и `ROOM_NAME`: комнаты и пароли берутся из каталога. Переменные нужны только для `rooms:init` при первичной регистрации старой комнаты. После миграции пользователям потребуется один раз войти заново, потому что cookie стала комнатной.

### Управление комнатами

```sh
npm run rooms:list
npm run rooms:create -- --name "Новая кампания" --system pbta-2d6
npm run rooms:create -- --name "Некроника" --system nechronica
npm run rooms:disable -- <room-id>
npm run rooms:enable -- <room-id>
npm run rooms:archive -- <room-id>
npm run rooms:delete -- <room-id> --yes
```

- `rooms:create` требует `--name` и `--system` (`pbta-2d6` или `nechronica`), создаёт каталог атомарно через временный `rooms/.creating-*`, фиксирует систему и только после успешной проверки добавляет запись в каталог. Код подключения показывается один раз; пароль вводится скрыто в TTY или одной строкой через stdin. Флаг `--gm-password` намеренно отсутствует, чтобы секрет не попадал в историю shell.
- `rooms:list` показывает ID, имя, систему, статус и дату создания. Коды, HMAC и хэши паролей не выводятся.
- `rooms:disable` запрещает новые входы и запросы, не удаляя данные. `rooms:enable` возвращает активную или отключённую комнату в работу; архивированную включить нельзя.
- `rooms:archive` требует подтверждения (`yes`) либо `--yes`, создаёт финальную резервную копию, закрывает соединения, оставляет данные на диске и переводит комнату в `archived`. Восстановление archived-комнаты — это restore её копии в новую комнату, а не повторное включение.
- `rooms:delete` удаляет каталог комнаты и запись каталога. Активную или отключённую комнату можно удалить только с `--force`; архивную — без него. Подтверждение — ввод точного ID комнаты либо `--yes`. По умолчанию создаётся финальная копия, а все backups комнаты переносятся в `data/deleted-rooms/<room-id>-<время>/` вместе с `room.json`; `--no-backup` отключает только новую финальную копию. Удаление необратимо для рабочей комнаты, но сохранённые копии можно восстановить в новую комнату той же системы.
- Все команды работают с тем же каталогом, что и сервер, и не требуют его перезапуска.

## Установка и настройка

```sh
nvm use
npm ci
cp .env.example .env
```

Заполните `.env` для первичной настройки:

- `ROOM_NAME` — имя существующей комнаты `default`.
- `ROOM_CODE` — 6–8 букв/цифр из алфавита без `O`, `0`, `I`, `1` (регистр ввода не важен). Старые коды длиной от 12 символов остаются совместимы.
- `GM_PASSWORD` — пароль ведущего, минимум 10 символов. Парольные фразы с дефисами подходят.

Эти три переменные нужны команде `npm run rooms:init` для регистрации существующей комнаты `default`. После неё обычный сервер работает без них: комнаты, коды и пароли хранятся в каталоге. Новые комнаты создаются CLI `rooms:create`, а не через `.env`.

Секреты не передаются клиенту. Не публикуйте `.env` и не коммитьте его в Git. `server-secret` и `catalog.sqlite` создаются с правами `0600`; не копируйте `server-secret` отдельно от каталога.

### Переменные окружения

| Имя | Обязательная | По умолчанию | Назначение |
|---|---:|---|---|
| `ROOM_CODE` | Только для `rooms:init` | — | Код существующей комнаты `default`: 6–8 допустимых символов или совместимый старый код от 12 символов |
| `GM_PASSWORD` | Только для `rooms:init` | — | Пароль ведущего комнаты `default`, не короче 10 символов |
| `ROOM_NAME` | Нет | `Игровая комната` | Имя существующей комнаты `default` при регистрации в каталоге |
| `HOST` | Нет | `127.0.0.1` | Адрес прослушивания. Для ngrok достаточно `127.0.0.1` |
| `PORT` | Нет | `4321` | Порт сайта, API и WebSocket |
| `APP_DATA_DIR` | Нет | `./data` | Корень данных приложения; комнаты лежат в `<APP_DATA_DIR>/rooms/<room-id>/` |
| `SESSION_DAYS` | Нет | `30` | Срок сессии, 1–365 дней |
| `MAX_UPLOAD_MB` | Нет | `25` | Лимит изображения, 1–250 MB |
| `MAX_OPEN_ROOMS` | Нет | `8` | Максимум одновременно открытых SQLite комнат, 1–64 |
| `PUBLIC_ORIGIN` | Нет | — | Публичные Origin через запятую, например `https://example.ngrok-free.app`. Нужен для ngrok |
| `TRUST_PROXY` | Нет | `false` | Доверять `X-Forwarded-*`. Включайте только если сервер доступен исключительно через локальный прокси |
| `NODE_ENV` | Нет | `development` | `npm start` выставляет `production` автоматически |

`PUBLIC_ORIGIN` принимает только `http(s)`-origin без пути, query и hash. `npm start` проверяет наличие `dist/index.html`, инициализированный каталог и `server-secret`; при ошибке сервер завершается с понятным сообщением, не выводя секреты.

## Локальная разработка

```sh
npm run dev
```

Команда собирает Astro, затем запускает backend с перезапуском при изменениях в `server/`. Откройте `http://127.0.0.1:4321` (или фактический `HOST`/`PORT` из `.env`). Dev-режим использует обычные HTTP-cookie без `Secure`, чтобы работать локально.

## Production-запуск

```sh
npm run build
npm start
```

- `npm run build` собирает статический frontend в `dist/` и сервер в `dist-server/`.
- `npm start` выставляет `NODE_ENV=production` и запускает `dist-server/server/index.js`.
- Fastify раздаёт `dist/`, API и WebSocket на одном порту из `.env`.
- Неизвестные `/api/*` и `/ws` маршруты возвращают JSON 404, отсутствующие файлы с расширением — 404, остальные пути получают SPA-оболочку `index.html`.
- Внутренние ошибки не раскрывают стек и детали; в лог пишется только серверная информация.
- Production-сборка не зависит от Vite HMR и dev-сервера.

Повторяйте `npm run build` после изменений frontend или backend. Для локальной production-проверки по HTTP cookie автоматически остаются без `Secure`; при реальном HTTPS через ngrok `Secure` включается.

## Публичный доступ через ngrok (macOS Intel)

Игрокам нужен только обычный браузер и публичная HTTPS-ссылка. Устанавливать Node.js, ngrok или проект им не требуется.

### 1. Установка

Вариант с Homebrew:

```sh
brew install ngrok/ngrok/ngrok
```

Либо скачайте архив для macOS Intel (`darwin-amd64`) со страницы <https://ngrok.com/download>, распакуйте и положите `ngrok` в каталог из `PATH`, например `/usr/local/bin`.

### 2. Первоначальная настройка

Создайте бесплатный аккаунт ngrok, скопируйте authtoken из личного кабинета и выполните:

```sh
ngrok config add-authtoken <ваш-токен>
```

Токен хранится локально в конфигурации ngrok. Не добавляйте его в `.env` проекта и не коммитьте.

### 3. Сборка и запуск сервера

Сначала соберите production-версию:

```sh
npm ci
npm run build
```

Узнайте фактический порт из конфигурации проекта — не предполагайте, что это всегда `4321`:

```sh
grep '^PORT=' .env
```

Если `PORT` не задан, используется `4321`. Запустите `npm start` в отдельном терминале.

### 4. Туннель на фактический порт

Во втором терминале запустите ngrok, подставив порт из `.env`:

```sh
ngrok http <PORT>
```

Например, если в `.env` указано `PORT=4321`, команда будет `ngrok http 4321`. Ngrok покажет публичный HTTPS-адрес вида `https://random-name.ngrok-free.app`.

Если сервер ещё не запущен, туннель всё равно создастся; до старта `npm start` запросы будут получать ошибку прокси.

### 5. Укажите публичный Origin и перезапустите сервер

Скопируйте выданный HTTPS-origin в `.env`:

```sh
PUBLIC_ORIGIN=https://random-name.ngrok-free.app
```

Затем перезапустите `npm start`. Это обязательный шаг при бесплатном ngrok: адрес меняется после перезапуска туннеля, и сервер должен принимать новый Origin.

Если у вас зарезервированный домен ngrok, адрес стабилен — обновите `PUBLIC_ORIGIN` один раз. Можно указать несколько origin через запятую.

Альтернатива: `TRUST_PROXY=true` позволяет серверу брать публичный host/protocol из `X-Forwarded-*`. Включайте это только когда локальный порт доступен исключительно через ngrok (например, `HOST=127.0.0.1`, без доступа из локальной сети), и понимаете последствия. Рекомендуемый и более предсказуемый вариант — `PUBLIC_ORIGIN`.

При `TRUST_PROXY=false` все запросы через ngrok выглядят для сервера как `127.0.0.1`, поэтому общий rate limit считается на всю комнату. Для 3–6 игроков этого обычно достаточно; при интенсивных загрузках можно включить `TRUST_PROXY=true` только при закрытом локальном порте, чтобы ограничения считались по реальным клиентам.

### 6. Подключение игроков

Передайте игрокам публичную ссылку `https://random-name.ngrok-free.app`, код комнаты и их имена. Пароль ведущего им не нужен. Бесплатный ngrok может показать предупреждающую страницу перед переходом на сайт — это нормально.

После входа клиент сам открывает `/room/<room-id>`; игроку не нужно вводить ID комнаты вручную. Один и тот же браузер может держать несколько комнат в разных вкладках — каждая получит свою cookie `tb_session_<roomId>`.

Ведущий входит с ролью GM и паролем, игроки — с ролью Player. При первом открытии браузер получает сессионную cookie; после перезагрузки страницы сессия восстанавливается.

### 7. Проверка WebSocket

- В интерфейсе индикатор соединения должен показывать подключение.
- В DevTools → Network → WS запрос `/ws` должен завершиться статусом `101 Switching Protocols`.
- Переместите объект или сделайте бросок: изменения должны появиться у остальных участников без обновления страницы.
- Отключите и включите сеть на клиенте: клиент переподключится, получит актуальное состояние комнаты и не создаст дублирующих обработчиков.
- Проверьте загрузку изображения, заметку с ограниченным доступом, личную заметку игрока и лист персонажа.

Проверка Origin для HTTP и WebSocket использует `PUBLIC_ORIGIN`; без него запросы с публичного адреса отклоняются с 403. `X-Forwarded-*` по умолчанию игнорируются, поэтому подмена заголовков не обходит проверку.

### 8. Завершение сессии

1. Завершите игру и при необходимости создайте резервную копию (см. ниже).
2. Остановите ngrok: `Ctrl+C` в терминале туннеля.
3. Остановите сервер: `Ctrl+C` в терминале `npm start`.
4. Публичная ссылка перестанет работать. Сессии и данные комнаты сохранятся на диске.

Если нужен постоянный адрес, настройте reserved domain в ngrok и используйте его в `PUBLIC_ORIGIN`.

## Безопасность

- Каждый HTTP-запрос и WebSocket-команда проверяют сессию, роль и комнату на сервере. `roomId` из клиента сверяется с каталогом и cookie; чужой ID не даёт доступа.
- Каталог хранит только HMAC-коды и `scrypt`-хэши GM-паролей. Открытые коды и пароли не пишутся в БД, логи, CLI-вывод и ответы API. Код новой комнаты показывается один раз при создании.
- `server-secret` — 32+ случайных байта, права `0600`, создаётся только при инициализации. Каталог без секрета не открывается. Резервная копия каталога хранит `catalog.sqlite` и `server-secret` вместе.
- Вход ограничен rate limit, а ошибки нейтральны: сервер не сообщает, существует ли комната с таким кодом, и не перечисляет комнаты.
- Сессионная cookie: `HttpOnly`, `SameSite=Strict`, `Path=/`, имя `tb_session_<roomId>`; `Secure` включается только при фактическом HTTPS. Logout одной комнаты не удаляет cookie и сессии других комнат.
- Origin проверяется для изменяющих HTTP-запросов и WebSocket. Разрешены прямой host запроса и явно указанные `PUBLIC_ORIGIN`.
- `X-Forwarded-*` учитываются только при `TRUST_PROXY=true`.
- Игрок не может редактировать заблокированные слои, чужие объекты, чужие стикеры и неназначенные листы.
- Приватные заметки, личные заметки игроков и их изображения выдаются только после серверной проверки доступа; посторонний игрок не видит их в списке, снимке комнаты или по прямому запросу.
- Изображение без разрешения на перемещение не участвует в hit-testing у игрока и не блокирует интерактивные объекты под ним; выбор ведущего по активному слою от этого флага не зависит.
- Удалять листы и ресурсы библиотеки может только ведущий; сервер повторно проверяет роль, назначение листа и все фактические ссылки на изображение.
- Изображения дедуплицируются и проверяются в пределах своей комнаты. Знание чужого `assetId` не позволяет получить файл: сначала проверяется запись в БД этой комнаты.
- Менять общий фон доски может только ведущий; игрок получает обновление через WebSocket, но команда отклоняется сервером.
- Вызывать и закрывать боевую карту (`room:scene:set`) может только ведущий. Игрок не может отправлять команды в неактивную сцену и не получает содержимое боевой карты до её вызова; GM-only слои и объекты проверяются на сервере.
- Ресурсы боевой карты доступны игроку только когда боевая карта активна и объект находится на публичном видимом слое.
- Листы персонажей фильтруются по закреплённой системе и её версии. Листы другой системы сохраняются в базе, но не попадают в снимок комнаты и обычные API и не редактируются. PbtA-специфичные команды и поля (`characteristics`, `fate`, `counter:*`, `ability:*`) отклоняются для листов Nechronica.
- После первой фиксации игровую систему нельзя сменить через интерфейс, HTTP или WebSocket: сервер отвечает `409 ROOM_SYSTEM_IMMUTABLE`. Обычные серверные методы также не предоставляют сеттер. Несовпадение системы даёт `409 SYSTEM_MISMATCH`.
- Изменение размера метки проверяет роль, блокировку слоя, минимальные размеры и пропорции изображения.
- Кубики генерируются на сервере; результат, бонус и автор проверяются.
- Загрузки проверяют MIME, сигнатуру, размеры и путь; файлы выдаются по правам текущей проекции.
- Отключённая или архивированная комната не открывает новые сессии и закрывает активные WebSocket-соединения. Проверка статуса выполняется на каждом запросе, а не только при старте.

## Резервное копирование и восстановление

Резервная копия комнаты включает SQLite-снимок, все оригиналы изображений и manifest. SQLite копируется через online backup API `better-sqlite3`, поэтому снимок согласован даже при работающем сервере; простое копирование одного файла базы не используется.

Manifest v2 дополнительно содержит `roomId`, `roomName`, `systemId`, `systemVersion`, `schemaVersion` и контрольные суммы файлов. Restore проверяет, что копия принадлежит выбранной комнате и совпадает с её закреплённой системой. Копии старого формата `version: 1` читаются, но требуют явного указания целевой комнаты.

Сначала соберите сервер, если `dist-server/` отсутствует или устарел:

```sh
npm run build
npm run rooms:list
npm run backup -- --room <room-id>
npm run backup:list -- --room <room-id>
```

`backup` создаёт `data/rooms/<room-id>/backups/<timestamp>/` и проверяет, что база открывается, проходит `integrity_check`/`foreign_key_check`, а все упомянутые в базе изображения присутствуют и совпадают по размеру и SHA-256.

### Восстановление комнаты

**Остановите сервер** перед восстановлением. Затем:

```sh
npm run backup:list -- --room <room-id>
npm run backup:restore -- --room <room-id> <имя-копии>
```

Команда проверит копию до любых изменений и сверит `roomId` и системную пару, запросит подтверждение (введите `yes`) и создаст страховочную копию текущего состояния `pre-restore-*`. Только после этого база и каталог `assets/` заменяются согласованно; при ошибке выполняется откат. Для неинтерактивного запуска добавьте `--yes`:

```sh
npm run backup:restore -- --room <room-id> <имя-копии> --yes
```

Не используйте `--yes` без понимания, что текущая комната будет заменена. Восстановление затрагивает только выбранную комнату; другие комнаты и каталог не меняются.

### Восстановление удалённой комнаты

`rooms:delete` сохраняет backups в `data/deleted-rooms/<room-id>-<время>/backups/` и `room.json` с именем, системой и временем удаления. Код и пароль удалённой комнаты восстановить нельзя, поэтому создайте новую комнату с той же системой:

```sh
npm run rooms:create -- --name "Восстановленная" --system pbta-2d6
cp -R "data/deleted-rooms/<удалённая>-<время>/backups/<имя-копии>" "data/rooms/<новый-id>/backups/"
npm run backup:restore -- --room <новый-id> <имя-копии> --accept-room-mismatch --yes
```

`--accept-room-mismatch` разрешает восстановить копию с прежним `roomId` в новую комнату, но по-прежнему требует совпадения игровой системы. Сервер должен быть остановлен.

### Каталог и полная установка

Каталог и `server-secret` — отдельная пара. Их копия без игровых данных создаётся командой:

```sh
npm run catalog:backup
npm run catalog:list
npm run catalog:restore -- <имя-копии> [--yes]
```

Восстанавливайте каталог **только при остановленном сервере** и только вместе с его `server-secret`: старый секрет с новым каталогом (или наоборот) сделает коды комнат недействительными. Полная копия установки включает каталог, секрет и все комнаты:

```sh
npm run install:backup
npm run install:list
npm run install:verify -- <имя>
```

`install:backup` создаёт копию в `data/catalog-backups/` и сразу проверяет её. Автоматического restore всей установки нет: это согласованная ручная операция при остановленном сервере. Порядок — остановить сервер, сохранить текущий `data/`, восстановить каталог и нужные комнаты из проверенной копии, затем запустить сервер. Не смешивайте `catalog.sqlite` и `server-secret` из разных копий.

### Проверка восстановления в отдельном каталоге

Чтобы проверить копию, не затрагивая рабочую установку:

```sh
TMP_DIR="$(mktemp -d)"
cp -R data/. "$TMP_DIR"/
APP_DATA_DIR="$TMP_DIR" npm run backup:list -- --room <room-id>
APP_DATA_DIR="$TMP_DIR" npm run backup:restore -- --room <room-id> <имя-копии> --yes
PORT=4400 APP_DATA_DIR="$TMP_DIR" npm start
```

`PORT=4400` нужен только чтобы временная проверка не конфликтовала с уже запущенным сервером. После проверки остановите временный сервер и удалите `TMP_DIR`. Каталог `data/`, включая `catalog-backups/` и комнатные `backups/`, исключён из Git через `.gitignore`.

## Поведение этапов 1–5

- **Этап 1.** Ведущий и игроки подключаются по коду комнаты; сессии хранятся на сервере и восстанавливаются после перезагрузки. Статус WebSocket показывает переподключение.
- **Этап 2.** Бесконечный холст с личным pan/zoom; PNG, JPEG и WebP с проверкой сигнатуры и лимитом размера; SHA-256-дедупликация; неразрушающая обрезка, отражение, пропорции и свободное растяжение; слои с видимостью, блокировкой и аудиторией; права объектов проверяются сервером.
- **Этап 3.** Заметки с доступом `gm-only`, `all-players`, `selected-players`; текст и изображения запрашиваются только при открытии; метки и стикеры синхронизируются; игрок управляет только своими стикерами. Игроки ведут личные заметки без меток и координат: список и содержимое доступны только владельцу и ведущему, а ведущий видит записи игроков только для чтения. Видимость панели заметок хранится только в интерфейсе участника и не зависит от бросков или общих обновлений.
- **Этап 4.** Реестр системных и дополнительных модулей; закреплённая за комнатой система `pbta-2d6`; серверные броски 2d6, Превосходство/Угнетение, Помеха, критические результаты, «Сила Судьбы», свободные броски и общая история последних 10 событий, включая применения способностей.
- **Этап 5.** Несколько листов у игрока, неназначенные листы ведущего, назначение/переназначение/снятие, просмотр и редактирование, характеристики с интеграцией в бросок, счётчики и способности. Лист и окно броска — плавающие панели; позиция хранится локально у каждого участника и не синхронизируется.
- **Многокомнатность (этап 4).** `catalog.sqlite` и `server-secret`, HMAC-коды и scrypt-пароли, CLI комнат, ленивый `RoomManager` с LRU и leases, комнатные cookie, `/room/<room-id>`, room-scoped localStorage, полная изоляция HTTP/WS и backup/restore по комнате. Существующая `default` регистрируется идемпотентно через `rooms:init`. `rooms:delete` удаляет комнату с предварительной копией в `data/deleted-rooms/`.

## Дополнительные функции

- **Фон доски.** Компактный селектор ведущего переключает серый или чёрный фон рабочей области. Выбор хранится в `room.background`, восстанавливается после перезапуска и рассылается всем участникам через `room:state`. Игрок не может отправить изменение.
- **Удаление неназначенных листов.** В каталоге ведущего у неназначенного листа есть кнопка «Удалить» с подтверждением и именем персонажа. Сервер проверяет роль и `assignedPlayerId === null`, удаляет лист вместе со счётчиками и способностями в транзакции. Изображения библиотеки остаются.
- **Удаление ресурсов.** Ведущий может удалить неиспользуемое изображение из библиотеки. Диалог показывает миниатюру, имя файла и найденные ссылки. Сервер проверяет объекты доски, вложения и метки заметок, портреты и изображения способностей; при наличии ссылок возвращает `409`. Оригинал и производные файлы удаляются безопасной последовательностью с откатом при ошибке.
- **Размер меток заметок.** Кнопка «Изменить размер» показывает маркеры трансформации. Текст переносится без изменения шрифта, изображения сохраняют пропорции, минимальные размеры проверяются на клиенте и сервере. `Escape` отменяет изменение и возвращает прежний размер; размер сохраняется в `note_markers.width/height` и синхронизируется через WebSocket.
- **Взаимодействие игроков с изображениями.** Изображение на доступном слое перехватывает указатель у игрока только при включённом разрешении на перемещение. Без него изображение остаётся видимым, но не выделяется, не перемещается, не масштабируется и не обрезается; клик проходит к холсту, и камера панорамируется прямо над изображением. Перекрывающее неинтерактивное изображение не блокирует доступное изображение под ним. Ведущий сохраняет выбор по активному слою независимо от этого флага.
- **Личные заметки игроков.** В меню «Создать» у игрока есть «Заметка»: личная запись без метки, координат и слоя. Игрок создаёт, открывает, редактирует и удаляет только свои заметки; ведущий видит все записи, сгруппированные по авторам, но не может их менять. Список фильтруется на сервере по владельцу, содержимое и вложения запрашиваются отдельными защищёнными запросами, а общие обновления комнаты не содержат приватного текста. Вложение можно убрать из заметки, не удаляя оригинал из библиотеки.
- **Сгруппированная верхняя панель.** Действия разделены на группы «Вид доски», «Боевая карта», «Игровые инструменты», «Персонажи и материалы» и «Пользовательские действия». Заметка и стикер объединены в меню «Создать», а при нехватке ширины хвостовые группы переезжают в «Ещё» без горизонтальной прокрутки. Выпадающие меню позиционируются у границ окна и при нехватке места открываются вверх.
- **Боевая карта.** Доступна только в комнате Nechronica, потому что системный модуль объявляет `capabilities.battleMap`. В PbtA группа меню, кнопки и предпросмотр отсутствуют, а сервер отклоняет прямые команды со сценой `battle`. В Nechronica меню ведущего «Боевая карта» содержит локальное редактирование, глобальный вызов и возврат на основную доску. Боевая карта хранит собственный фон и набор слоёв; её можно наполнять изображениями, стикерами и метками заметок теми же инструментами, что и основную доску. Пока карта не вызвана, игроки не получают её данные. Предпросмотр ведущего не переключает участников и сопровождается баннером «изменения не переключают игроков».
- **Nechronica (этап 1).** Система зарегистрирована как независимый модуль с собственной версией и версией схемы листа. Она может быть однократно закреплена за новой комнатой вместо PbtA; после фиксации смена системы недоступна. Лист персонажа использует общую плавающую панель, заголовок, просмотр/редактирование, закрытие и локальное состояние, но вместо механики показывает заглушку «Лист персонажа Nechronica — находится в разработке». Меню бросков показывает заглушку «Система бросков Nechronica — находится в разработке», не содержит полей PbtA и не создаёт записей бросков. Листы других систем сохраняются, но скрываются из обычных API и не редактируются.
- **Светлая и тёмная тема интерфейса.** В меню «Ещё» есть переключатель «Светлая / Тёмная». Выбор применяется сразу без перезагрузки и хранится только в браузере участника (`tabletop:ui:v1:<roomId>:<participantId>:theme`), поэтому у ведущего и игроков он независим, не синхронизируется через WebSocket и не попадает в состояние комнаты. По умолчанию используется светлая тема; некорректное сохранённое значение безопасно сбрасывается к ней. Тема оформляет панели, меню, листы, заметки, броски и диалоги, но не меняет фон игровой доски и цвета пользовательских стикеров, меток и текстов.
- **Применение способностей в общей истории.** В карточке способности есть кнопка «Применить», доступная назначенному игроку и ведущему. Событие `ability-use` попадает в ту же ленту, что и броски, и хранит снимок имён, картинки, краткого и полного описания, автора, времени и шрифта. Применение не бросает кубики и не меняет счётчики или чекбоксы. Полное описание раскрывается локально.
- **Общий лимит истории.** В SQLite остаются 10 последних событий всех типов: PbtA, свободные броски и применения способностей. При добавлении одиннадцатого самое старое удаляется в той же транзакции; существующие ссылки `rerollOf` у оставшихся записей сохраняются.
- **Шрифт Caveat.** Варианты «Стандартный» (по умолчанию) и «Caveat» доступны для стикеров, текста заметок, имён листов и названий/описаний способностей. Файлы шрифта лежат в `public/fonts/` вместе с `OFL.txt` и не зависят от CDN. Шрифт сохраняется вместе с объектом или полем, старые записи получают стандартный; Konva перерисовывает стикеры после загрузки шрифта.

## Известные ограничения

- Несколько комнат работают на одном сервере, но административного веб-интерфейса нет: создание, статусы, архивирование и удаление выполняются только CLI.
- `rooms:delete` удаляет данные безвозвратно, но по умолчанию оставляет финальную копию и все прежние backups в `data/deleted-rooms/`. Если нужно освободить место полностью, удалите этот каталог вручную после проверки. Удаление выполняйте при остановленном сервере, чтобы гарантированно освободить файловые дескрипторы.
- Динамической загрузки системных модулей нет: PbtA и Nechronica по-прежнему статически импортируются и попадают в начальный код. Это отдельный будущий этап.
- Перенос персонажей и листов между комнатами, конвертация систем и несколько систем в одной комнате не реализованы. Система фиксируется один раз при создании/миграции комнаты.
- Restore каталога и полной установки — ручная операция при остановленном сервере. Автоматического «одной командой» восстановления всей установки нет, чтобы не смешать `catalog.sqlite` и `server-secret` из разных копий.
- Копия каталога не содержит игровых данных по дизайну. Для полного снимка используйте `install:backup`, а для отдельной комнаты — `backup --room`.
- После перехода на комнатные cookie пользователям нужен однократный повторный вход. Это неизбежное следствие того, что старый `tb_session` больше не определяет комнату.
- Старая раскладка `data/room.sqlite` больше не открывается сервером: перед первым запуском новой версии выполните `npm run room:migrate`, затем `npm run rooms:init` при остановленном сервере. Старые файлы сохраняются для отката.
- Игровая система фиксируется один раз. Смена системы, версии или переход в режим «без системы» после фиксации недоступны без отдельной контролируемой миграции.
- Старые броски без однозначной системной атрибуции остаются историческими: они видны в ленте с пометкой, но не запускают механику и не могут быть повторены.
- Нет сетки.
- Боевая карта пока не содержит сетки, токенов, инициативы и боевых бросков; это отдельная сцена доски с теми же инструментами, что и основная.
- Nechronica на этом этапе — только независимый модуль и заглушки листа/бросков. Полные правила, структура листа и механика бросков не реализованы.
- Браузерных end-to-end тестов в репозитории нет: многокомнатная проверка выполнялась отдельным CDP-скриптом в Chrome и live-скриптом на реальном сервере. Вёрстку, перетаскивание панелей, выпадающие меню, перенос групп в «Ещё», предпросмотр боевой карты и отрисовку Caveat в Konva нужно периодически проверять глазами в обычном браузере.
- Внешний туннель ngrok и WebSocket через публичный HTTPS требуют ручной проверки на машине с установленным ngrok и учётной записью; в текущем окружении они не проверялись.
- При бесплатном ngrok публичный адрес меняется, поэтому `PUBLIC_ORIGIN` нужно обновлять и перезапускать сервер, либо использовать reserved domain.
