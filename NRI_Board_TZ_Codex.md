## 0. Инструкция для Codex

Создай отдельное приложение для совместной игры в настольные ролевые игры через браузер.

Перед началом работы:

1. Проверь текущую папку и существующие файлы. Если там уже есть другой проект, не изменяй его и не пытайся встроить доску в него. Это отдельное приложение и отдельный репозиторий.
2. Проверь версии macOS, Node.js и npm, доступные в окружении. Выбери совместимую поддерживаемую LTS-версию Node.js. Не используй экспериментальные релизы.
3. Прочитай всё это ТЗ. Сначала предложи короткий план и структуру проекта, после чего реализуй первый этап. Не пытайся написать всё приложение одним большим изменением.
4. Не добавляй функции, не указанные в ТЗ, без необходимости. При выборе между простой и сложной реализацией предпочитай простую, если она не нарушает требования.
5. После каждого этапа запускай проверки типов, тесты и production build. Исправляй ошибки до перехода к следующему этапу.
6. Не оставляй фиктивные кнопки, неработающие обработчики или данные-заглушки в функциях, которые заявлены как готовые.
7. Документируй команды запуска, структуру данных, переменные окружения и способ создания резервной копии.

**Важно:** приложение должно запускаться на MacBook Pro 13-inch (2018, Intel), работать на одном домашнем компьютере ведущего и обслуживать небольшую группу примерно из 3–6 участников. Оно не должно требовать облачной базы данных, внешнего аккаунта или платного хостинга.

## 1. Цель и общая концепция

Разработать лёгкую минималистичную веб-доску для небольших игровых сессий НРИ. Ведущий запускает сервер на своём MacBook, а остальные участники подключаются к комнате через браузер по публичной ссылке ngrok.

Приложение — это прежде всего **совместный графический редактор игрового пространства**, а не универсальная виртуальная игровая платформа. Основной приоритет — удобное размещение изображений и управление слоями во время игры, приватные заметки, листы персонажей и простой бросок кубиков.

### Главные принципы

- Минимальный, спокойный и функциональный интерфейс без визуального перегруза.
- Desktop-first: основная работа предполагается на компьютерах и ноутбуках.
- Низкая нагрузка на CPU, RAM и сеть.
- Один сервер у ведущего; браузеры игроков получают обновления в реальном времени.
- Сохранение состояния игры на диске ведущего.
- Приватность обеспечивается сервером, а не только скрытием элементов интерфейса.
- Базовые функции не зависят от конкретной игровой системы.
- Игровые системы и независимые дополнительные возможности подключаются как разные виды встроенных модулей.

## 2. Рекомендуемый технический стек

Использовать существующий опыт проекта Astro + TypeScript, но создать **новый независимый проект**.

### Frontend

- Astro для структуры страниц и сборки.
- TypeScript для клиентской логики.
- Konva.js для двумерной рабочей области: изображения, текстовые объекты, перетаскивание, трансформации и обработка событий.
- Обычные CSS и HTML для панелей, меню, форм и диалогов.
- Не подключать React/Vue/Svelte без объективной необходимости. Не добавлять UI-библиотеки только ради нескольких компонентов.

Konva подходит, поскольку предоставляет объекты сцены, события, drag-and-drop, трансформирование и отдельные canvas-слои. При этом игровые слои приложения всё равно должны быть собственной моделью данных, а не зависеть напрямую от внутренних слоёв Konva.

### Backend

- Node.js + TypeScript.
- Fastify для HTTP API и раздачи собранного frontend.
- WebSocket для синхронизации действий участников в реальном времени.
- Один HTTP(S)-совместимый серверный порт для сайта, API и WebSocket.

Astro можно собирать в static output, а собранную папку `dist` раздавать через Fastify. Это позволит не усложнять проект SSR-адаптером, но сохранить полноценный Node.js backend.

### Хранение данных

- SQLite для состояния комнаты, игроков, слоёв, объектов, заметок, листов персонажей, модулей и истории бросков.
- Файлы изображений хранить отдельно в локальной папке данных приложения.
- Не хранить бинарные изображения непосредственно в JSON или SQLite.
- Путь к данным задавать через конфигурацию; папка данных должна быть исключена из Git.

### Общие требования к коду

- Строгий TypeScript.
- Разделить frontend, backend, общие типы и игровые модули.
- Все изменения общего состояния проходят через сервер.
- Не использовать внешнюю облачную базу данных или облачное хранилище.
- Версии зависимостей фиксировать lock-файлом.

## 3. Комнаты и подключение участников

### Первая версия

- Одна постоянная игровая комната на одном запущенном сервере.
- Один ведущий (GM) и несколько игроков.
- Ведущий запускает сервер локально.
- Игроки подключаются из браузера по ссылке ngrok и вводят имя/код комнаты.
- Не требуется регистрация через сторонние сервисы.
- Игрок после перезагрузки страницы может восстановить своё подключение, если у него сохранилась сессия браузера.
- Если соединение потеряно, клиент показывает статус переподключения и после восстановления получает актуальное состояние комнаты.

### Роли

**GM / Ведущий:**
- Управляет всей доской, слоями и объектами.
- Создаёт и редактирует заметки и интерактивные метки.
- Создаёт несколько листов персонажей, в том числе неназначенных, полностью заполняет их и редактирует любой лист.
- Назначает, переназначает и снимает назначение листов между игроками.
- Видит неназначенные листы, которые не передаются игрокам.
- Настраивает игровые модули.
- Может видеть все данные комнаты.

**Player / Игрок:**
- Видит только опубликованную ему часть доски.
- Не видит панель слоёв и GM-only заметки.
- Может двигать только те объекты, для которых ему разрешено перемещение.
- Может создавать несколько собственных листов персонажей; созданный лист сразу назначается ему.
- Редактирует только назначенные ему листы; остальные назначенные листы доступны только для просмотра.
- Может совершать броски кубиков.
- Может пользоваться общими интерактивными заметками, если они ему доступны.

По умолчанию игрок не может редактировать произвольные изображения и слои ведущего. Для отдельных объектов должна быть возможность разрешить перемещение конкретному игроку или всем игрокам.

### Авторизация и безопасность

- Ведущий задаёт секрет ведущего/пароль комнаты через локальную конфигурацию или безопасный первоначальный мастер настройки.
- Не передавать GM-секрет клиентскому JavaScript.
- Использовать случайные идентификаторы сессий; по возможности хранить сессионный токен в защищённой cookie.
- Проверять права пользователя на каждом API-запросе и WebSocket-сообщении.
- Проверять Origin для WebSocket-подключений.
- Не считать скрытый пункт интерфейса защитой данных.
- Данные приватных заметок, GM-only слоёв и неназначенных листов персонажей не должны отправляться игрокам даже в виде скрытого JSON. Назначенные листы доступны всем участникам комнаты в режиме просмотра.
- Ограничить число попыток ввода пароля/кода комнаты.

## 4. Общая игровая доска

### Рабочая область

- Одна общая двумерная рабочая область без обязательной сетки.
- По умолчанию сетка выключена и не отображается.
- Рабочая область должна ощущаться как бесконечный холст: перемещение камеры и масштабирование без фиксированных границ.
- Масштабирование колесом мыши относительно положения курсора.
- Перемещение камеры перетаскиванием пустой области (например, средней кнопкой мыши или с зажатой клавишей Space).
- Кнопка возврата к масштабу 100% и кнопка «показать всё содержимое».
- Координаты и положение объектов общие для всех участников.
- Масштаб и положение камеры каждого участника локальные: перемещение камеры одним игроком не должно перемещать камеру остальных.
- Сетка в будущем реализуется как отдельный необязательный Feature Module.

### Объекты на доске

В первой версии поддержать следующие типы объектов:

1. Изображение.
2. Текстовый стикер.
3. Интерактивная метка/точка заметки.

Каждый объект имеет уникальный ID, тип, позицию, размеры, принадлежность слою, порядок внутри слоя и данные доступа.

### Управление объектами

- Выбрать объект нажатием.
- Перемещать объект перетаскиванием.
- Изменять ширину и высоту маркерами трансформации.
- Предусмотреть сохранение пропорций при изменении размера и возможность свободного растягивания.
- Обрезать изображение в отдельном режиме редактирования. Обрезка должна быть неразрушающей: исходный файл не меняется.
- Отражать изображение горизонтально и вертикально.
- Удалять объект.
- Дублировать объект на доске без дублирования физического файла.
- Переносить объект на другой слой через панель слоёв или контекстное меню.
- Изменения должны синхронизироваться с участниками в реальном времени.

Не реализовывать в первой версии фильтры изображений, сложную цветокоррекцию, свободное рисование по изображению или полноценный редактор пикселей.

## 5. Изображения и библиотека ресурсов

### Поддерживаемые форматы первой версии

- PNG.
- JPG / JPEG.
- WebP.

**WebM:** это видеоформат, а не статичное изображение. Поддержку WebM отложить на отдельный следующий этап. Архитектура ресурсов должна позволять добавить тип `video` позже, но не нужно задерживать первую версию ради видео.

### Библиотека ресурсов

- Ведущий может загрузить изображение с компьютера.
- Загруженные файлы доступны через библиотеку ресурсов.
- При добавлении файла на доску создаётся новый объект, ссылающийся на уже загруженный ресурс.
- Один ресурс можно разместить на доске несколько раз; каждый экземпляр редактируется независимо.
- Исходный файл не должен изменяться при перемещении, масштабировании, отражении или обрезке экземпляров.

### Дедупликация

Не использовать только имя файла как критерий дублирования.

1. При загрузке вычислять SHA-256 содержимого файла.
2. Если в библиотеке уже существует ресурс с таким хэшем и типом, не сохранять повторный бинарный файл.
3. Создать новый объект доски, ссылающийся на существующий ресурс.
4. Если имена совпали, а хэши различаются, считать это разными изображениями.
5. Сохранять исходное имя файла как метаданные для отображения.
6. Нельзя удалять физический ресурс, пока на него ссылаются объекты доски, заметки или листы персонажей.

### Загрузка и хранение

- Начальный лимит размера файла — 25 MB, вынести в конфигурацию.
- Проверять MIME-тип и фактическую сигнатуру файла; не полагаться только на расширение.
- Защититься от некорректных имён файлов и path traversal.
- Сохранять файлы под внутренним ID или хэшем, а не под пользовательским именем.
- Выдавать файлы через контролируемый endpoint с проверкой доступа. Проверять доступ не только к ID файла, но и к конкретному объекту/заметке/листу, через который ресурс используется.
- Библиотека исходных ресурсов и её полный список доступны только GM; игрок получает только те файлы, которые используются в доступных ему объектах, заметках или листах.
- Не допускать чтения приватного файла простым подбором или копированием URL.
- Показывать пользователю понятную ошибку при неподдерживаемом формате или превышении лимита.

## 6. Система слоёв (только GM)

Панель слоёв доступна исключительно ведущему. Игроки не должны видеть её, список слоёв, GM-only слои или скрытые метаданные слоёв.

### Функции панели

- Создать слой.
- Переименовать слой.
- Удалить слой.
- Перетаскивать слой выше или ниже других слоёв.
- Переключать видимость слоя (иконка глаза).
- Блокировать и разблокировать слой (иконка замка).
- Выбирать активный слой, в который будут добавляться новые объекты.
- Показывать количество объектов в слое — необязательно, если это усложняет интерфейс.

Порядок в списке должен быть очевидным: верхний слой отображается над нижним.

### Семантика свойств слоя

- `visible`: выключает отображение слоя на игровой доске; слой остаётся в панели GM.
- `locked`: запрещает случайно выбирать и редактировать объекты слоя. Ведущий может снять блокировку.
- `audience`: `all` или `gm-only`. GM-only слой и его содержимое не передаются игрокам.

Удаление слоя не должно неожиданно удалять его объекты. Перед удалением предложить переместить объекты в другой слой или подтвердить удаление объектов.

### Порядок объектов

Внутри слоя объекты также имеют порядок от нижнего к верхнему. В первой версии достаточно базового порядка создания и возможности менять порядок объектов через команды «на передний план» и «на задний план» или соответствующие действия контекстного меню. Отдельный Photoshop-подобный список всех объектов внутри слоя не обязателен.

## 7. Интерактивные метки и заметки

Ведущий может разместить на доске интерактивную метку. При нажатии на неё открывается окно с заметкой.

### Содержимое заметки

- Заголовок.
- Текст.
- Одно или несколько изображений.
- Возможность редактировать и удалять содержимое ведущим.

### Права доступа к заметке

- `gm-only` — заметка и её содержимое доступны только ведущему.
- `all-players` — доступна всем игрокам комнаты.
- `selected-players` — доступна только выбранным игрокам.

GM может менять видимость заметки в любой момент.

### Поведение при нажатии

- Нажатие на метку открывает окно заметки только в браузере нажавшего пользователя.
- Сам факт открытия заметки не транслируется остальным игрокам.
- Содержимое заметки отправляется клиенту только в том случае, если у пользователя есть право его видеть.
- Игрок не может редактировать заметку ведущего.
- GM-only метка не должна отображаться игрокам.

## 8. Текстовые стикеры

Стикеры — самостоятельные объекты на общей доске.

### Функции

- Создать стикер.
- Ввести и редактировать текст.
- Перемещать стикер.
- Изменять размер.
- Удалять стикер.
- Использовать несколько заранее заданных спокойных цветов фона.
- Текст должен переноситься по ширине стикера.

### Права

- GM может создавать, редактировать, перемещать и удалять любые стикеры.
- Игрок может редактировать собственный стикер.
- Право создавать стикеры игроками должно включаться/выключаться ведущим в настройках комнаты.
- Изменения видны участникам, которым доступен соответствующий объект/слой.

## 9. Листы персонажей

Лист персонажа — самостоятельная сущность, связанная с системным игровым модулем. Его структура и особенности интерфейса определяются этим модулем, а не универсальным конструктором ядра. В первой версии реализован лист системного модуля `pbta-2d6`. Ограничение «один лист на игрока» отсутствует: игрок и ведущий могут создавать несколько листов.

### Модель данных и привязка

- Лист имеет собственный `id`, `creatorId`, `creatorName`, `assignedPlayerId`, `assignedPlayerName`, фактические `systemId`, `systemVersion`, `schemaVersion`, имя персонажа, портрет, характеристики, «Силу Судьбы», счётчики, способности, `createdAt` и `updatedAt`.
- `creatorId` — участник, создавший лист. `assignedPlayerId` — игрок, которому лист назначен; допускается `null`. Создатель и назначенный игрок различаются и не обязаны совпадать.
- Игрок создаёт лист от своего имени: сервер сам записывает его как создателя и сразу назначает ему лист. Игрок не может создать неназначенный или чужой лист.
- Ведущий создаёт неназначенные листы, полностью заполняет их и при необходимости назначает игрокам.
- Назначение — единственное основание прав игрока на лист. Клиентский `ownerId` или иной идентификатор владельца не принимается как доказательство прав.
- Неназначенные листы видны только ведущему и не передаются игрокам ни через `/api/sheets`, ни через снимок доски, ни через WebSocket — включая название, карточку и портрет.
- Назначенные листы доступны всем участникам комнаты: назначенный игрок и ведущий редактируют, остальные игроки только смотрят.
- Ведущий может назначить, переназначить и снять назначение. При снятии лист становится приватным для ведущего, его содержимое сохраняется. Права прежнего игрока отзываются немедленно.
- Изменение активной системы не удаляет и не преобразует существующие листы. При возврате к PbtA лист снова доступен.
- Общие механизмы хранения, синхронизации и проверки прав остаются частью ядра (`server/store.ts`, `server/sheets.ts`); структура конкретных полей задаётся модулем.
- Данные листов хранятся в SQLite и переживают перезапуск сервера; миграции существующей базы выполняются безопасно и не теряют данные комнаты.
- Не создавать универсальный конструктор листов: набор полей первой версии фиксирован модулем PbtA.

### Структура листа PbtA

- **Имя персонажа** — свободный текст до 80 символов.
- **Портрет** — необязательный `assetId` из библиотеки изображений.
- **Четыре характеристики** — «Могущество», «Познание», «Величие», «Воля». Значение — целое число, отображается со знаком: `+2`, `0`, `-1`.
- **«Сила Судьбы»** — отдельное целое числовое поле. Не списывается автоматически, не проверяется и не связано с повторным броском; расход учитывается вручную.
- **Дополнительные счётчики** — произвольный список с названием и целым значением; порядок задаётся вручную.
- **Особые способности** — произвольный список. У каждой есть ID, название, необязательная картинка, многострочное описание, необязательный числовой счётчик, необязательный чекбокс и порядок. Свёрнутость карточки способности — локальное состояние браузера (`localStorage`), оно не синхронизируется и не хранится на сервере.
- Размеры, лимиты и валидация значений проверяются сервером; клиент не является источником истины.

### Режимы просмотра и редактирования

- Лист всегда открывается в режиме просмотра. Режим не запоминается между открытиями.
- Отдельная кнопка «Редактировать» включает режим редактирования; понятная кнопка «Просмотр» возвращает обратно.
- В просмотре назначенный игрок и ведущий могут менять «Силу Судьбы», значения всех дополнительных счётчиков, числовые счётчики способностей и чекбоксы. Изменения сразу сохраняются и синхронизируются.
- Структурные изменения — создание, удаление и переименование счётчиков, создание и удаление способностей, их названия, описания, картинки и флаги, а также имя персонажа и портрет — доступны только в режиме редактирования.
- Чужие игроки видят лист только для просмотра; все value-команды и структурные команды проверяются сервером отдельно.

### Характеристики и окно броска

- Клик по названию характеристики открывает компактное окно броска поверх листа, выше по Z-index. Лист остаётся открытым в прежнем состоянии.
- Окно переиспользует существующие настройки PbtA: бонус характеристики подставляется, название характеристики видно, «Превосходство», «Угнетение» и «Помеха» сохраняются. Бросок выполняется только по кнопке.
- После закрытия окна броска лист остаётся в прежнем состоянии. Передача названия характеристики, бонуса, ID листа и ID владельца в существующую историю бросков сохраняется.
- «Превосходство», «Угнетение» и «Помеха» используются через существующий API модуля PbtA без новой системы бросков.
- Сервер проверяет, что бонус совпадает со значением характеристики в назначенном листе и что бросок выполняет назначенный игрок или ведущий от его имени.
- Повторный бросок сохраняет название характеристики, бонус, ID персонажа, владельца и модификаторы исходного броска.

### Плавающая панель листа

- Лист открывается как плавающая панель поверх доски, без блокирующей подложки. Поле доски вне панели остаётся доступным.
- Панель перетаскивается за заголовок, сворачивается в компактную полоску и закрывается отдельными кнопками. Z-index выше доски, но ниже окна броска.
- Одна панель переиспользуется для разных листов; открытие другого листа заменяет содержимое.
- Координаты, свёрнутость и открытость панели хранятся локально у каждого пользователя и не синхронизируются через WebSocket. При изменении размера окна панель не выходит за пределы экрана.

### Изображения

- Портрет и картинки способностей выбираются из существующей библиотеки.
- Загрузка нового изображения разрешена игроку для назначенного ему листа и его способностей; ведущий может загружать изображения как прежде.
- Дедупликация выполняется по SHA-256 содержимого и MIME-типу: повторная загрузка не создаёт новый бинарный файл.
- Игроку показываются только доступные ему ресурсы; сервер отдельно проверяет доступ к каждому изображению. Неназначенные листы и их изображения игроку недоступны.
- Нельзя удалять физический ресурс, пока на него ссылаются объекты доски, заметки, листы или способности.

### Каталог листов

- У игрока есть разделы «Мои персонажи» и «Другие персонажи», а также кнопка создания ещё одного листа.
- У ведущего отображаются все листы, назначенные и неназначенные, с созданием, редактированием, назначением, переназначением и снятием назначения.
- Карточка показывает имя персонажа, портрет и имя назначенного игрока либо «Не назначен».
- Открытие листа, свёрнутость способностей и положение панелей — локальное состояние браузера и не синхронизируются.
- Изменения общего листа рассылаются через существующий WebSocket и сохраняются в SQLite.

### Миграция существующих листов

- Старое ограничение `UNIQUE(owner_id, system_id)` удаляется.
- Старые поля `owner_id`/`owner_name` переходят в `creator_id`/`creator_name`; текущий владелец одновременно записывается в `assigned_player_id`/`assigned_player_name`.
- Сохраняются ID листов, содержимое, счётчики, способности и ссылки на изображения; дубликаты не создаются.
- После миграции выполняется проверка внешних ключей и целостности базы.

## 10. Игровые модули, кубики и модуль PbtA

Броски кубиков не должны быть частью ядра графической доски. Они реализуются отдельным подключаемым модулем правил.

### Архитектура модулей

Реестр встроенных модулей в ядре разделяет два независимых типа:

- **System Modules** — игровые системы, их правила и броски, настройки комнаты для выбранной системы и специфическая структура связанных с ней листов персонажей. Системный модуль имеет собственные стабильные `id` и `version`.
- **Feature Modules** — независимые возможности приложения, например сетка и дополнительные инструменты карты. Они не меняют правила и механику активной игровой системы, если такая интеграция явно не предусмотрена.

В первой версии в комнате выбирается одна основная игровая система; её `id` определяет активный системный модуль и системную принадлежность листов. Не поддерживать несколько одновременно активных основных систем.

- Использовать компактный типизированный реестр встроенных модулей и явные настройки включения/отключения. Не загружать сторонний исполняемый код, не создавать маркетплейс, динамический загрузчик или сложную систему плагинов.
- Настройки игровой системы комнаты и настройки дополнительных модулей отделяются от общих настроек комнаты.
- Отключение модуля скрывает его инструменты, но не удаляет автоматически сохранённую историю или данные.
- Сетка, когда она понадобится, подключается как необязательный Feature Module и по умолчанию выключена.

### Модуль `pbta-2d6`

Системный модуль содержит правила бросков и вычисление результатов. Бонус характеристики можно вводить вручную или подготовить из листа персонажа. Механика выносится в чистые функции, не зависящие от интерфейса, и принимает название характеристики, числовой бонус и ID персонажа/владельца. Не привязывать механику броска к заранее заданному набору характеристик.

Игровая комната при первоначальной настройке получает одну активную системную запись (`id` и `version`) либо режим без системы. Существующая комната настраивается ведущим без потери её текущих данных. Изменение активной системы — отдельное действие ведущего с предупреждением; сохранённые данные и история не преобразуются автоматически.

У каждого участника доступна компактная панель бросков с общей лентой. Панель располагается в правом нижнем углу доски, имеет собственную прокрутку и может сворачиваться; её состояние индивидуально для браузера. Скрытая панель показывает индикатор новых бросков. Новые записи идут сверху, без модального окна.

Обычный бросок:

`2d6 + введённый бонус`

Дополнительные параметры:

- **Превосходство:** +1 к итоговому результату.
- **Угнетение:** −1 к итоговому результату.
- **Помеха:** бросается 3d6, наибольший кубик отбрасывается, два оставшихся складываются; затем добавляется бонус и применимый модификатор.

Для Помехи бросать 3d6 и учитывать два наименьших кубика; бонус и ситуационный модификатор продолжают прибавляться. Превосходство и Угнетение — взаимоисключающие ситуационные модификаторы +1 и −1 соответственно, но оба могут сочетаться с Помехой.

### Интерфейс броска

- Поле ручного ввода бонуса (целое число, допускаются отрицательные значения).
- Селектор ситуационного модификатора: без модификатора, «Превосходство» или «Угнетение».
- Переключатель «Помеха».
- Кнопка броска.
- Ситуационный модификатор выбирается из трёх состояний: отсутствует, Превосходство (+1), Угнетение (−1).
- Помеха включается независимо и сочетается с выбранным ситуационным модификатором.
- После броска показывать исходные выпавшие значения, какие кубики были учтены, бонус, модификаторы, итоговую сумму и категорию результата; критический статус показывать отдельно.
- Бросок отправляется всем участникам в общую историю: имя игрока, результат, детали расчёта и время.
- Каждый игрок может бросать самостоятельно.
- Результат вычисляет сервер с использованием криптографически стойкого генератора случайных чисел Node.js, чтобы клиенты не могли подменить выпавшие значения.

### Результативные диапазоны

Результаты вычисляет системный модуль, а не ядро: итог до 6 включительно — «Неудача», от 7 до 9 — «Обычный успех», от 10 — «Триумфальный успех». Отдельно отмечать критический провал при двух учитываемых натуральных единицах и критический успех при двух учитываемых натуральных шестёрках. Критический статус определяется по результатам кубиков до модификаторов; при Помехе учитываются только два вошедших в сумму кубика.

### «Сила Судьбы» — повторный бросок

- Автор может повторить собственную проверку PbtA с тем же числом кубиков, бонусом, ситуационным модификатором и Помехой, но с новым независимым набором значений.
- Исходная запись остаётся неизменной; повтор сохраняется отдельной записью со ссылкой на исходный бросок и пометкой «Сила Судьбы».
- Не списывать и не проверять автоматически ресурс Силы Судьбы.

### Свободные броски

- Отдельный инструмент для бросков без категорий PbtA: 1–20 одинаковых кубиков форматов d4, d6, d8, d10, d12, d20 и d100.
- Показывать каждый результат и сумму. Все значения генерируются на сервере.
- Ведущий может выполнять свободные броски и проверки PbtA от имени выбранного игрока. Проверка использует те же правила PbtA и помечается именем ведущего и участника, за которого она выполнена. Самостоятельную проверку PbtA ведущий не выполняет.

### Генерация случайных значений и история

- Для всех бросков сервер использует `node:crypto` `randomInt()` и генерирует каждый кубик отдельно (`randomInt(1, sides + 1)`). Клиент передаёт только параметры; кубики, сумму, категорию и критический статус определяет сервер.
- Не принимать готовые значения кубиков и суммы. Для тестов генератор должен подменяться детерминированной функцией.
- В общей ленте показывать автора и участника броска, время, тип, выпавшие/учтённые кубики, отброшенный кубик, модификаторы, сумму, категорию, критический статус и связь повторного броска.
- Хранить в SQLite только 10 последних записей; при добавлении новой в одной транзакции удалять вышедшую за лимит запись. История сохраняется после перезапуска, не создавая архива.

## 11. Синхронизация в реальном времени

- Использовать WebSocket.
- Сервер является источником истины для общего состояния.
- При подключении клиент получает только разрешённую ему проекцию состояния комнаты.
- Изменения общего состояния рассылаются подключённым участникам.
- Во время перетаскивания допустимо отправлять промежуточные позиции с ограниченной частотой; окончательная позиция обязательно сохраняется по завершении действия.
- Состояние камеры и открытие/закрытие локальных окон не синхронизируются.
- Локальное открытие заметки не является общим событием.
- При переподключении клиент повторно получает актуальную разрешённую проекцию состояния.
- Если сервер отклоняет изменение из-за прав доступа, клиент возвращает объект к серверному состоянию и показывает понятное сообщение.

Не нужно реализовывать сложную CRDT-синхронизацию или совместное редактирование одного текста посимвольно. Для небольшой группы достаточно командного обновления состояния с проверкой прав на сервере.

## 12. Интерфейс и визуальный стиль

- Минималистичный интерфейс.
- Нейтральная палитра, чёткая типографика, аккуратные тонкие разделители.
- Без декоративных градиентов, тяжёлых теней и визуально шумных панелей.
- Рабочая область занимает основную часть экрана.
- Инструменты размещаются в компактной панели.
- Панель слоёв доступна только GM.
- Панели заметок, персонажей и бросков открываются по запросу и не должны постоянно занимать большую часть экрана.
- Предусмотреть понятное состояние соединения: Online / Reconnecting / Offline.
- Предусмотреть индикатор сохранения: Saved / Saving / Error.
- Не делать сложный адаптивный мобильный интерфейс в первой версии. Интерфейс должен оставаться работоспособным на планшете, но приоритет — desktop.

## 13. Что не входит в первую версию

Чтобы не раздувать проект, пока не реализовывать:

- Голосовой и видеочат.
- Встроенные листы характеристик с автоматическими формулами.
- Автоматизацию разных НРИ, кроме базового модуля PbtA 2d6.
- Обязательную сетку.
- WebM и другие видеоформаты на доске.
- Сложный туман войны и динамическое освещение.
- Полноценное рисование кистью, фильтры и пиксельное редактирование.
- Сторонние плагины, маркетплейс и загрузку исполняемого кода.
- Облачную синхронизацию между разными серверами.
- Систему аккаунтов с электронной почтой.
- Множество независимых комнат на одном сервере.

## 14. Фактическая структура проекта

Структура сохраняет разделение frontend, backend, общих типов и игровых модулей. Она компактнее первоначальной схемы: панели и состояние клиента находятся в одном `app.ts`, а серверные доменные операции — в небольших модулях.

```text
src/
  pages/index.astro        HTML-оболочка интерфейса
  client/app.ts            Konva-холст, все панели, WebSocket и локальное состояние
  shared/board.ts          Общие DTO и типы состояния
  shared/sheet-ui.ts       Чистые UI-хелперы листа, окна броска и localStorage
  modules/registry.ts      Реестр системных и дополнительных модулей
  modules/system/pbta-2d6/ PbtA: схема листа, расчёт бросков, тесты
  styles/global.css        Стили интерфейса
server/
  index.ts                 Fastify: HTTP, WebSocket, статика, Origin, ошибки
  auth.ts                  Аутентификация и сессии
  config.ts                Валидация окружения, PUBLIC_ORIGIN, TRUST_PROXY
  board.ts                 Проверка команд доски и прав
  sheets.ts                Листы и их value-команды
  store.ts                 SQLite, миграции, доменные операции
  assets.ts, images.ts     Загрузка, сигнатуры, SHA-256 и выдача файлов
  backup-lib.ts            SQLite backup API, проверка и атомарное восстановление
  backup.ts                CLI backup create / list / restore
  *.test.ts                Автотесты домена, HTTP, WebSocket, прав и UI-исходников
data/                      Runtime-данные; исключены из Git
  room.sqlite
  assets/<random-id>
  backups/<timestamp>/{room.sqlite,assets/,manifest.json}
```

Один процесс Fastify обслуживает `dist/`, `/api/*` и `/ws` на одном порту. SQLite использует `journal_mode = DELETE`; резервное копирование всё равно выполняется через online backup API, а не копированием файла. Сессии хранятся на сервере, cookie — `HttpOnly`/`SameSite=Strict`, `Secure` включается при фактическом HTTPS. Origin проверяется для изменяющих HTTP-запросов и WebSocket; `X-Forwarded-*` учитываются только при явном `TRUST_PROXY=true`.

### Этап 5 — листы персонажей, связанные с игровыми модулями

- Реализовать лист PbtA как самостоятельную сущность с `creatorId`/`creatorName`, назначаемым `assignedPlayerId`/`assignedPlayerName`, фактическими `id`/`version` модуля `pbta-2d6` и версии схемы листа.

**Критерий готовности:** игрок создаёт несколько листов, которые сразу назначаются ему, и редактирует только назначенные; ведущий создаёт неназначенные листы, полностью заполняет их, назначает, переназначает и снимает назначение. Неназначенные листы не попадают к игрокам ни через API, ни через WebSocket. Назначенные листы видны всем в просмотре, но value- и структурные изменения проверяются сервером. Лист открывается в просмотре, переключается в редактирование отдельной кнопкой, плавает над доской и не блокирует поле; окно броска открывается поверх него и подготавливает существующий бросок PbtA с корректными названием, бонусом, ID персонажа/владельца и модификаторами; «Сила Судьбы» не списывается автоматически. Данные и изображения синхронизируются, переживают перезапуск, миграции не теряют данные, а локальное состояние (свёрнутость, положение, открытые окна) не попадает на сервер.

Автоматические проверки проходят; внешний ngrok и визуальное перетаскивание панелей подтверждаются ручной проверкой.

## 16. Критерии качества и приёмки

Приложение считается пригодным для первой игровой сессии, когда:

1. GM и 3–6 участников могут одновременно подключиться к одной комнате.
2. Все видят изменения общей доски без ручного обновления страницы.
3. У каждого участника собственное положение и масштаб камеры.
4. GM может создавать, сортировать, скрывать и блокировать слои.
5. Игроки не видят список слоёв и не получают содержимое GM-only областей.
6. Одно изображение можно разместить несколько раз без повторной загрузки бинарного файла.
7. Изображения можно двигать, масштабировать, обрезать и отражать.
8. Заметки открываются локально и проверяют права на сервере.
9. В комнате выбирается одна основная система; её системный модуль определяется идентификатором и версией из встроенного реестра. Feature Modules не меняют механику системы без явной интеграции.
10. PbtA использует указанные категории и критические результаты; сервер генерирует кубики, вычисляет результат и сохраняет данные. Свободные броски не получают категории PbtA.
11. Листы — самостоятельные сущности с создателем и назначаемым игроком; структура PbtA включает имя, портрет, четыре характеристики, «Силу Судьбы», счётчики и способности; назначение и права проверяются сервером.
12. Игрок может иметь несколько листов; ведущий создаёт неназначенные листы, назначает и снимает назначение. Неназначенные листы не передаются игрокам. Назначенные видны всем для просмотра, но редактируют их только назначенный игрок и ведущий. Характеристики готовят существующий бросок PbtA, «Сила Судьбы» не списывается автоматически, а локальное состояние листа не синхронизируется.
13. После перезапуска сервера основные данные и изображения сохраняются.
14. Сборка production проходит без ошибок, TypeScript не содержит необъяснённых ошибок, основные проверки проходят.
15. `npm start` запускает собранный frontend, API и WebSocket на одном порту; неизвестные маршруты и ошибки обрабатываются предсказуемо.
16. Публичный HTTPS-origin явно разрешается через `PUBLIC_ORIGIN` или корректно настроенный `TRUST_PROXY`; произвольный Origin и подмена `X-Forwarded-*` без доверия прокси не проходят. Cookie остаются `HttpOnly`/`SameSite=Strict`, а `Secure` включается при HTTPS.
17. Резервная копия включает согласованный SQLite-снимок и все изображения; восстановление проверяет копию, создаёт страховочную копию и не оставляет частично заменённых данных.
18. `data/`, `.env`, `.sqlite`, изображения и резервные копии не попадают в Git.

## 17. Нерешённые детали и принятые допущения

Чтобы не блокировать старт разработки, в первой версии приняты следующие решения:

- **Помеха:** в модуле PbtA бросить 3d6 и сложить два наименьших кубика. Бонус характеристики и ситуационный модификатор сохраняются.
- **WebM:** не входит в первую версию; статичные PNG/JPG/JPEG/WebP важнее.
- **Права игроков на доске:** по умолчанию игроки не редактируют произвольные объекты ведущего; ведущий может разрешать перемещение отдельных объектов, а создание собственных стикеров игроками можно включить отдельно.
- **Комнаты:** одна комната на один сервер в первой версии.
- **Сетка:** отсутствует в ядре и выключена; позднее подключается модулем.
- **Публичность листа:** назначение — единственное основание прав игрока. Назначенные листы видны всем участникам, редактируют их назначенный игрок и ведущий; неназначенные видит только ведущий. Создатель-игрок без назначения прав не сохраняет. Модель прав общая, а содержание и структура листа зависят от системного модуля.
- **ngrok:** публичный адрес задаётся через `PUBLIC_ORIGIN`; при бесплатном тарифе он меняется после перезапуска туннеля. `TRUST_PROXY=true` остаётся опцией для случая, когда сервер доступен только через локальный прокси, и по умолчанию выключен.
- **Резервные копии:** восстановление выполняется только при остановленном сервере. Приложение проверяет копию и создаёт `pre-restore-*`, но не управляет внешним хранением и ротацией старых копий.

Эти решения не должны мешать последующему расширению приложения.
