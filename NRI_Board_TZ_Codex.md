## 1. Цель и общая концепция

Разработать лёгкую минималистичную веб-доску для небольших игровых сессий НРИ. Ведущий запускает сервер на своём MacBook, а остальные участники подключаются к комнате через браузер по публичной ссылке ngrok.

Приложение — это прежде всего **совместный графический редактор игрового пространства**, а не универсальная виртуальная игровая платформа. Основной приоритет — удобное размещение изображений и управление слоями во время игры, приватные заметки, листы персонажей и простой бросок кубиков.

### Главные принципы

- Минимальный, спокойный и функциональный интерфейс без визуального перегруза.
- Desktop-first: основная работа предполагается на компьютерах и ноутбуках.
- Низкая нагрузка на CPU, RAM и сеть.
- Один сервер у ведущего; браузеры игроков получают обновления в реальном времени.
- Сохранение состояния игры на диске ведущего.
- Приватность обеспечивается сервером, а не только скрытием элементов интерфейса.
- Базовые функции не зависят от конкретной игровой системы.
- Игровые системы и независимые дополнительные возможности подключаются как разные виды встроенных модулей.

## 2. Рекомендуемый технический стек

Использовать существующий опыт проекта Astro + TypeScript, но создать **новый независимый проект**.

### Frontend

- Astro для структуры страниц и сборки.
- TypeScript для клиентской логики.
- Konva.js для двумерной рабочей области: изображения, текстовые объекты, перетаскивание, трансформации и обработка событий.
- Обычные CSS и HTML для панелей, меню, форм и диалогов.
- Не подключать React/Vue/Svelte без объективной необходимости. Не добавлять UI-библиотеки только ради нескольких компонентов.

Konva подходит, поскольку предоставляет объекты сцены, события, drag-and-drop, трансформирование и отдельные canvas-слои. При этом игровые слои приложения всё равно должны быть собственной моделью данных, а не зависеть напрямую от внутренних слоёв Konva.

### Backend

- Node.js + TypeScript.
- Fastify для HTTP API и раздачи собранного frontend.
- WebSocket для синхронизации действий участников в реальном времени.
- Один HTTP(S)-совместимый серверный порт для сайта, API и WebSocket.

Astro можно собирать в static output, а собранную папку `dist` раздавать через Fastify. Это позволит не усложнять проект SSR-адаптером, но сохранить полноценный Node.js backend.

### Хранение данных

- SQLite для состояния комнаты, игроков, слоёв, объектов, заметок, листов персонажей, модулей и истории бросков.
- Файлы изображений хранить отдельно в локальной папке данных приложения.
- Не хранить бинарные изображения непосредственно в JSON или SQLite.
- Путь к данным задавать через конфигурацию; папка данных должна быть исключена из Git.

### Общие требования к коду

- Строгий TypeScript.
- Разделить frontend, backend, общие типы и игровые модули.
- Все изменения общего состояния проходят через сервер.
- Не использовать внешнюю облачную базу данных или облачное хранилище.
- Версии зависимостей фиксировать lock-файлом.

## 3. Комнаты и подключение участников

### Текущая версия

- Один сервер обслуживает несколько независимых комнат; каждая комната имеет
  собственный `RoomStore`, SQLite, изображения, backups, участников и сессии.
- Комната определяется кодом при входе. Каталог `data/catalog.sqlite` хранит
  HMAC-код, scrypt-хэш пароля GM, систему и статус; игровых данных в каталоге
  нет.
- ID комнаты — стабильная случайная строка (UUID для новых комнат), а не имя.
  Клиент после входа открывает `/room/<room-id>`.
- В каждой комнате один ведущий (GM) и несколько игроков.
- Ведущий запускает сервер локально и управляет комнатами через CLI.
- Игроки подключаются из браузера по ссылке ngrok и вводят имя/код комнаты.
- Не требуется регистрация через сторонние сервисы.
- Игрок после перезагрузки страницы может восстановить своё подключение, если у
  него сохранилась сессия браузера. Один браузер может держать несколько комнат
  в разных вкладках.
- Если соединение потеряно, клиент показывает статус переподключения и после
  восстановления получает актуальное состояние своей комнаты.

### Роли

**GM / Ведущий:**
- Управляет всей доской, слоями и объектами.
- Создаёт и редактирует заметки и интерактивные метки.
- Видит личные заметки всех игроков, сгруппированные по авторам, но не может редактировать или удалять чужие записи.
- Создаёт несколько листов персонажей, в том числе неназначенных, полностью заполняет их и редактирует любой лист.
- Назначает, переназначает и снимает назначение листов между игроками.
- Видит неназначенные листы, которые не передаются игрокам.
- Настраивает игровые модули.
- Может видеть все данные комнаты.

**Player / Игрок:**
- Видит только опубликованную ему часть доски.
- Не видит панель слоёв и GM-only заметки.
- Может двигать только те объекты, для которых ему разрешено перемещение. Изображение без такого разрешения остаётся видимым, но не перехватывает указатель, поэтому камера панорамируется прямо над ним.
- Создаёт, открывает, редактирует и удаляет только свои личные заметки без меток и координат.
- Может создавать несколько собственных листов персонажей; созданный лист сразу назначается ему.
- Редактирует только назначенные ему листы; остальные назначенные листы доступны только для просмотра.
- Может совершать броски кубиков.
- Может пользоваться общими интерактивными заметками, если они ему доступны.

По умолчанию игрок не может редактировать произвольные изображения и слои ведущего. Для отдельных объектов должна быть возможность разрешить перемещение конкретному игроку или всем игрокам.

### Авторизация и безопасность

- Ведущий задаёт секрет ведущего/пароль комнаты через локальную конфигурацию или безопасный первоначальный мастер настройки.
- Не передавать GM-секрет клиентскому JavaScript.
- Использовать случайные идентификаторы сессий; по возможности хранить сессионный токен в защищённой cookie.
- Проверять права пользователя на каждом API-запросе и WebSocket-сообщении.
- Проверять Origin для WebSocket-подключений.
- Не считать скрытый пункт интерфейса защитой данных.
- Данные приватных заметок, GM-only слоёв и неназначенных листов персонажей не должны отправляться игрокам даже в виде скрытого JSON. Назначенные листы доступны всем участникам комнаты в режиме просмотра.
- Личные заметки игроков доступны только владельцу и GM. Список фильтруется на сервере для каждой сессии; текст и вложения запрашиваются через защищённые endpoint'ы и не попадают в общую рассылку `room:state`.
- Ограничить число попыток ввода пароля/кода комнаты.
- Код комнаты хранится только как HMAC-SHA256 с `server-secret`; новый код — 8 символов из безопасного алфавита. Нейтральная ошибка входа не сообщает, существует ли комната. Вход ограничен rate limit.
- Пароль GM хранится как scrypt-хэш с солью и проверяется constant-time; открытый пароль не попадает в БД, логи и клиент.
- Кука называется `tb_session_<roomId>` и действует только для своей комнаты. Logout одной комнаты не удаляет сессии других комнат. При HTTPS cookie получает `Secure`.
- `roomId` из клиента проверяется по каталогу, статусу и сессии; знание чужого ID или `assetId` не даёт доступа.

## 4. Общая игровая доска

### Рабочая область

- Одна общая двумерная рабочая область без обязательной сетки.
- По умолчанию сетка выключена и не отображается.
- Рабочая область должна ощущаться как бесконечный холст: перемещение камеры и масштабирование без фиксированных границ.
- Масштабирование колесом мыши относительно положения курсора.
- Перемещение камеры перетаскиванием пустой области (например, средней кнопкой мыши или с зажатой клавишей Space).
- Кнопка возврата к масштабу 100% и кнопка «показать всё содержимое».
- Координаты и положение объектов общие для всех участников.
- Масштаб и положение камеры каждого участника локальные: перемещение камеры одним игроком не должно перемещать камеру остальных.
- Сетка в будущем реализуется как отдельный необязательный Feature Module.

### Фон рабочей области

- Доступны два нейтральных варианта: серый (по умолчанию, сохраняет прежний вид `#e9ece8`) и чёрный.
- Компактный селектор фона виден только ведущему. Игроки не могут отправить изменение даже прямым WebSocket-сообщением.
- Выбор хранится в `room.background`, входит в снимок комнаты и рассылается всем участникам через существующий `room:state`.
- Смена фона меняет только CSS-фон рабочей области. Камера, масштаб, координаты и размеры объектов, слои, заметки, метки и стикеры не затрагиваются.
- После повторного входа и перезапуска сервера восстанавливается сохранённый вариант.

### Объекты на доске

В первой версии поддержать следующие типы объектов:

1. Изображение.
2. Текстовый стикер.
3. Интерактивная метка/точка заметки.

Каждый объект имеет уникальный ID, тип, позицию, размеры, принадлежность слою, порядок внутри слоя и данные доступа.

### Управление объектами

- Выбрать объект нажатием.
- Перемещать объект перетаскиванием.
- Изменять ширину и высоту маркерами трансформации.
- Предусмотреть сохранение пропорций при изменении размера и возможность свободного растягивания.
- Обрезать изображение в отдельном режиме редактирования. Обрезка должна быть неразрушающей: исходный файл не меняется.
- Отражать изображение горизонтально и вертикально.
- Удалять объект.
- Дублировать объект на доске без дублирования физического файла.
- Переносить объект на другой слой через панель слоёв или контекстное меню.
- Изменения должны синхронизироваться с участниками в реальном времени.

Изображение на доступном игроку слое участвует в hit-testing только при включённом разрешении на перемещение. Без разрешения оно остаётся видимым, но не выделяется, не перемещается, не масштабируется и не обрезается; нажатие проходит к рабочей области и запускает панорамирование камеры. Неинтерактивное изображение не блокирует интерактивные объекты под ним. Ведущий сохраняет выбор по активному слою независимо от этого флага.

Не реализовывать в первой версии фильтры изображений, сложную цветокоррекцию, свободное рисование по изображению или полноценный редактор пикселей.

## 5. Изображения и библиотека ресурсов

### Поддерживаемые форматы первой версии

- PNG.
- JPG / JPEG.
- WebP.

**WebM:** это видеоформат, а не статичное изображение. Поддержку WebM отложить на отдельный следующий этап. Архитектура ресурсов должна позволять добавить тип `video` позже, но не нужно задерживать первую версию ради видео.

### Библиотека ресурсов

- Ведущий может загрузить изображение с компьютера.
- Загруженные файлы доступны через библиотеку ресурсов.
- При добавлении файла на доску создаётся новый объект, ссылающийся на уже загруженный ресурс.
- Один ресурс можно разместить на доске несколько раз; каждый экземпляр редактируется независимо.
- Исходный файл не должен изменяться при перемещении, масштабировании, отражении или обрезке экземпляров.

### Дедупликация

Не использовать только имя файла как критерий дублирования.

1. При загрузке вычислять SHA-256 содержимого файла.
2. Если в библиотеке уже существует ресурс с таким хэшем и типом, не сохранять повторный бинарный файл.
3. Создать новый объект доски, ссылающийся на существующий ресурс.
4. Если имена совпали, а хэши различаются, считать это разными изображениями.
5. Сохранять исходное имя файла как метаданные для отображения.
6. Нельзя удалять физический ресурс, пока на него ссылаются объекты доски, заметки или листы персонажей.

### Удаление ресурсов библиотеки

- Удаление доступно только ведущему; кнопка находится в библиотеке ресурсов рядом с каждым изображением.
- Перед подтверждением клиент показывает имя файла, миниатюру и список фактического использования. Диалог предупреждает, что оригинальный файл удаляется без возможности восстановления из приложения.
- Сервер не доверяет клиентскому подтверждению и самостоятельно проверяет ссылки из `board_objects`, `note_assets`, `notes.marker_asset_id`, `character_sheets.portrait_asset_id` и `character_abilities.asset_id`. Если есть хотя бы одна ссылка, удаление запрещается с `409`; принудительного удаления нет.
- `GET /api/assets/:id/usage` отдаёт сводку использования только ведущему. `DELETE /api/assets/:id` повторно проверяет роль и ссылки.
- Удаление выполняется безопасной последовательностью: проверка пути внутри `data/rooms/default/assets/`, переименование оригинала и производных файлов во временные имена, удаление записи SQLite в транзакции, затем удаление временных файлов. При ошибке записи или файловой системы запись и файлы восстанавливаются.
- Путь проверяется через `resolve`/`dirname`; принимаются только файлы с именем `<asset-id>`, `<asset-id>.*` и `<asset-id>-*`. Посторонние файлы и изображения с совпадающим именем не затрагиваются.
- Дедупликация по SHA-256 и MIME сохраняется: удаляется только конкретная запись ресурса, а не все объекты с тем же содержимым.

### Загрузка и хранение

- Начальный лимит размера файла — 25 MB, вынести в конфигурацию.
- Проверять MIME-тип и фактическую сигнатуру файла; не полагаться только на расширение.
- Защититься от некорректных имён файлов и path traversal.
- Сохранять файлы под внутренним ID или хэшем, а не под пользовательским именем.
- Выдавать файлы через контролируемый endpoint с проверкой доступа. Проверять доступ не только к ID файла, но и к конкретному объекту/заметке/листу, через который ресурс используется.
- Библиотека исходных ресурсов и её полный список доступны только GM; игрок получает только те файлы, которые используются в доступных ему объектах, заметках или листах.
- Не допускать чтения приватного файла простым подбором или копированием URL.
- Показывать пользователю понятную ошибку при неподдерживаемом формате или превышении лимита.

## 6. Система слоёв (только GM)

Панель слоёв доступна исключительно ведущему. Игроки не должны видеть её, список слоёв, GM-only слои или скрытые метаданные слоёв.

### Функции панели

- Создать слой.
- Переименовать слой.
- Удалить слой.
- Перетаскивать слой выше или ниже других слоёв.
- Переключать видимость слоя (иконка глаза).
- Блокировать и разблокировать слой (иконка замка).
- Выбирать активный слой, в который будут добавляться новые объекты.
- Показывать количество объектов в слое — необязательно, если это усложняет интерфейс.

Порядок в списке должен быть очевидным: верхний слой отображается над нижним.

### Семантика свойств слоя

- `visible`: выключает отображение слоя на игровой доске; слой остаётся в панели GM.
- `locked`: запрещает случайно выбирать и редактировать объекты слоя. Ведущий может снять блокировку.
- `audience`: `all` или `gm-only`. GM-only слой и его содержимое не передаются игрокам.

Удаление слоя не должно неожиданно удалять его объекты. Перед удалением предложить переместить объекты в другой слой или подтвердить удаление объектов.

### Порядок объектов

Внутри слоя объекты также имеют порядок от нижнего к верхнему. В первой версии достаточно базового порядка создания и возможности менять порядок объектов через команды «на передний план» и «на задний план» или соответствующие действия контекстного меню. Отдельный Photoshop-подобный список всех объектов внутри слоя не обязателен.

## 7. Интерактивные метки и заметки

Заметки делятся на два типа: `board` — обычная заметка ведущего с меткой на доске, и `personal` — личная запись игрока без размещения на доске.

Ведущий может разместить на доске интерактивную метку. При нажатии на неё открывается окно с заметкой.

### Содержимое заметки

- Заголовок.
- Текст.
- Одно или несколько изображений.
- Возможность редактировать и удалять содержимое ведущим.

### Права доступа к заметке

- `gm-only` — заметка и её содержимое доступны только ведущему.
- `all-players` — доступна всем игрокам комнаты.
- `selected-players` — доступна только выбранным игрокам.

GM может менять видимость заметки в любой момент.

### Личные заметки игроков

- Тип `personal`: заголовок, текст, необязательные изображения и шрифт. У личной заметки нет метки, координат, слоя и настроек аудитории.
- Игрок создаёт, открывает, редактирует и удаляет только собственные записи. GM видит все записи, сгруппированные по авторам, но не может менять или удалять чужие.
- Метаданные личных заметок фильтруются на сервере для каждой сессии: игрок получает только свои, GM — все. Текст и изображения выдаются отдельными защищёнными запросами; посторонний игрок получает `404`.
- Личные заметки не попадают в общий список досковых заметок и не могут получить метку даже прямым запросом.
- Редактор, библиотека изображений и SHA-256-дедупликация переиспользуются. Удаление вложения из заметки убирает только ссылку и не удаляет оригинал из библиотеки.
- Панель заметок открывается без перезагрузки: у игрока показан раздел своих записей, у GM — переключатель «Мои заметки» / «Заметки игроков».

### Поведение при нажатии

- Нажатие на метку открывает окно заметки только в браузере нажавшего пользователя.
- Сам факт открытия заметки не транслируется остальным игрокам.
- Содержимое заметки отправляется клиенту только в том случае, если у пользователя есть право его видеть.
- Игрок не может редактировать заметку ведущего.
- GM-only метка не должна отображаться игрокам.

### Размер метки на доске

- При выборе метки рядом с «Редактировать» и «Удалить» доступна отдельная кнопка «Изменить размер».
- Режим показывает маркеры трансформации вокруг метки. Изменение размера не открывает заметку и не включает редактирование её содержимого; окно просмотра заметки не меняет размер.
- Текстовая метка меняет ширину и высоту, текст переносится по словам без масштабирования шрифта. Минимум — `64×34`.
- Графическая метка сохраняет исходные пропорции изображения; минимум — `24×24`. Клиент и сервер дополнительно проверяют пропорции и максимум `4000`.
- `Escape` отменяет режим и возвращает прежние размеры. Завершение трансформации сохраняет `width`/`height` в `note_markers` и синхронизирует их через WebSocket.
- Изменение разрешено ведущему и только на незаблокированном слое. Игрок получает отказ сервера, если пытается изменить метку напрямую.

## 8. Текстовые стикеры

Стикеры — самостоятельные объекты на общей доске.

### Функции

- Создать стикер.
- Ввести и редактировать текст.
- Перемещать стикер.
- Изменять размер.
- Удалять стикер.
- Использовать несколько заранее заданных спокойных цветов фона.
- Текст должен переноситься по ширине стикера.
- Для текста доступны варианты шрифта «Стандартный» и «Caveat»; выбранный шрифт хранится вместе со стикером и перерисовывается в Konva после загрузки файла.

### Права

- GM может создавать, редактировать, перемещать и удалять любые стикеры.
- Игрок может редактировать собственный стикер.
- Право создавать стикеры игроками должно включаться/выключаться ведущим в настройках комнаты.
- Изменения видны участникам, которым доступен соответствующий объект/слой.

## 9. Листы персонажей

Лист персонажа — самостоятельная сущность, связанная с системным игровым модулем. Его структура и особенности интерфейса определяются этим модулем, а не универсальным конструктором ядра. В первой версии реализован лист системного модуля `pbta-2d6`. Ограничение «один лист на игрока» отсутствует: игрок и ведущий могут создавать несколько листов.

### Модель данных и привязка

- Лист имеет собственный `id`, `creatorId`, `creatorName`, `assignedPlayerId`, `assignedPlayerName`, фактические `systemId`, `systemVersion`, `schemaVersion`, имя персонажа, портрет, характеристики, «Силу Судьбы», счётчики, способности, `createdAt` и `updatedAt`.
- `creatorId` — участник, создавший лист. `assignedPlayerId` — игрок, которому лист назначен; допускается `null`. Создатель и назначенный игрок различаются и не обязаны совпадать.
- Игрок создаёт лист от своего имени: сервер сам записывает его как создателя и сразу назначает ему лист. Игрок не может создать неназначенный или чужой лист.
- Ведущий создаёт неназначенные листы, полностью заполняет их и при необходимости назначает игрокам.
- Назначение — единственное основание прав игрока на лист. Клиентский `ownerId` или иной идентификатор владельца не принимается как доказательство прав.
- Неназначенные листы видны только ведущему и не передаются игрокам ни через `/api/sheets`, ни через снимок доски, ни через WebSocket — включая название, карточку и портрет.
- Назначенные листы доступны всем участникам комнаты: назначенный игрок и ведущий редактируют, остальные игроки только смотрят.
- Ведущий может назначить, переназначить и снять назначение. При снятии лист становится приватным для ведущего, его содержимое сохраняется. Права прежнего игрока отзываются немедленно.
- Изменение системы после фиксации невозможно и не удаляет существующие листы. Листы другой системы сохраняются в базе, но скрываются из обычных списков, снимка комнаты и API и не редактируются; при выборе PbtA доступны только её листы.
- Общие механизмы хранения, синхронизации и проверки прав остаются частью ядра (`server/store.ts`, `server/sheets.ts`); структура конкретных полей задаётся модулем.
- Данные листов хранятся в SQLite и переживают перезапуск сервера; миграции существующей базы выполняются безопасно и не теряют данные комнаты.
- Не создавать универсальный конструктор листов: набор полей первой версии фиксирован модулем PbtA.

### Структура листа PbtA

- **Имя персонажа** — свободный текст до 80 символов.
- **Портрет** — необязательный `assetId` из библиотеки изображений.
- **Четыре характеристики** — «Могущество», «Познание», «Величие», «Воля». Значение — целое число, отображается со знаком: `+2`, `0`, `-1`.
- **«Сила Судьбы»** — отдельное целое числовое поле. Не списывается автоматически, не проверяется и не связано с повторным броском; расход учитывается вручную.
- **Дополнительные счётчики** — произвольный список с названием и целым значением; порядок задаётся вручную.
- **Особые способности** — произвольный список. У каждой есть ID, название, необязательная картинка, многострочное описание, необязательный числовой счётчик, необязательный чекбокс, шрифт и порядок. Свёрнутость карточки способности — локальное состояние браузера (`localStorage`), оно не синхронизируется и не хранится на сервере.
- **Применение способности** — отдельная команда `sheet:ability:apply`, доступная назначенному игроку и ведущему. Она добавляет в общую историю событие `ability-use` со снимком имени персонажа и способности, картинки, краткого и полного описания, автора, времени и шрифта. Применение не бросает кубики и не изменяет счётчик или чекбокс. Полное описание раскрывается в истории локально.
- **Шрифт листа и способностей** — «Стандартный» (по умолчанию) или локальный Caveat; применяется к уместным именам, тексту заметок и описаниям способностей, а не ко всему интерфейсу.
- Размеры, лимиты и валидация значений проверяются сервером; клиент не является источником истины.

### Режимы просмотра и редактирования

- Лист всегда открывается в режиме просмотра. Режим не запоминается между открытиями.
- Отдельная кнопка «Редактировать» включает режим редактирования; понятная кнопка «Просмотр» возвращает обратно.
- В просмотре назначенный игрок и ведущий могут менять «Силу Судьбы», значения всех дополнительных счётчиков, числовые счётчики способностей и чекбоксы. Изменения сразу сохраняются и синхронизируются.
- Структурные изменения — создание, удаление и переименование счётчиков, создание и удаление способностей, их названия, описания, картинки и флаги, а также имя персонажа и портрет — доступны только в режиме редактирования.
- Чужие игроки видят лист только для просмотра; все value-команды и структурные команды проверяются сервером отдельно.

### Характеристики и окно броска

- Клик по названию характеристики открывает компактное окно броска поверх листа, выше по Z-index. Лист остаётся открытым в прежнем состоянии.
- Окно переиспользует существующие настройки PbtA: бонус характеристики подставляется, название характеристики видно, «Превосходство», «Угнетение» и «Помеха» сохраняются. Бросок выполняется только по кнопке.
- После закрытия окна броска лист остаётся в прежнем состоянии. Передача названия характеристики, бонуса, ID листа и ID владельца в существующую историю бросков сохраняется.
- «Превосходство», «Угнетение» и «Помеха» используются через существующий API модуля PbtA без новой системы бросков.
- Сервер проверяет, что бонус совпадает со значением характеристики в назначенном листе и что бросок выполняет назначенный игрок или ведущий от его имени.
- Повторный бросок сохраняет название характеристики, бонус, ID персонажа, владельца и модификаторы исходного броска.

### Плавающая панель листа

- Лист открывается как плавающая панель поверх доски, без блокирующей подложки. Поле доски вне панели остаётся доступным.
- Панель перетаскивается за заголовок, сворачивается в компактную полоску и закрывается отдельными кнопками. Z-index выше доски, но ниже окна броска.
- Одна панель переиспользуется для разных листов; открытие другого листа заменяет содержимое.
- Координаты, свёрнутость и открытость панели хранятся локально у каждого пользователя и не синхронизируются через WebSocket. При изменении размера окна панель не выходит за пределы экрана.

### Изображения

- Портрет и картинки способностей выбираются из существующей библиотеки.
- Загрузка нового изображения разрешена игроку для назначенного ему листа и его способностей; ведущий может загружать изображения как прежде.
- Дедупликация выполняется по SHA-256 содержимого и MIME-типу: повторная загрузка не создаёт новый бинарный файл.
- Игроку показываются только доступные ему ресурсы; сервер отдельно проверяет доступ к каждому изображению. Неназначенные листы и их изображения игроку недоступны.
- Нельзя удалять физический ресурс, пока на него ссылаются объекты доски, заметки, листы или способности.

### Каталог листов

- У игрока есть разделы «Мои персонажи» и «Другие персонажи», а также кнопка создания ещё одного листа.
- У ведущего отображаются все листы, назначенные и неназначенные, с созданием, редактированием, назначением, переназначением и снятием назначения.
- Ведущий может удалить только неназначенный лист. Кнопка удаления показывается рядом с такими листами и запрашивает подтверждение с именем персонажа и предупреждением о необратимости.
- Сервер проверяет роль GM, существование листа и `assignedPlayerId === null`. Назначенный лист отклоняется даже при прямом запросе. Удаление выполняется в транзакции и каскадно очищает счётчики и способности; изображения библиотеки не удаляются.
- Карточка показывает имя персонажа, портрет и имя назначенного игрока либо «Не назначен».
- Открытие листа, свёрнутость способностей и положение панелей — локальное состояние браузера и не синхронизируются.
- Изменения общего листа рассылаются через существующий WebSocket и сохраняются в SQLite.

### Миграция существующих листов

- Старое ограничение `UNIQUE(owner_id, system_id)` удаляется.
- Старые поля `owner_id`/`owner_name` переходят в `creator_id`/`creator_name`; текущий владелец одновременно записывается в `assigned_player_id`/`assigned_player_name`.
- Сохраняются ID листов, содержимое, счётчики, способности и ссылки на изображения; дубликаты не создаются.
- После миграции выполняется проверка внешних ключей и целостности базы.

## 10. Игровые модули, кубики и модуль PbtA

Броски кубиков не должны быть частью ядра графической доски. Они реализуются отдельным подключаемым модулем правил.

### Архитектура модулей

Реестр встроенных модулей в ядре разделяет два независимых типа:

- **System Modules** — игровые системы, их правила и броски, настройки комнаты для выбранной системы и специфическая структура связанных с ней листов персонажей. Системный модуль имеет собственные стабильные `id` и `version`.
- **Feature Modules** — независимые возможности приложения, например сетка и дополнительные инструменты карты. Они не меняют правила и механику активной игровой системы, если такая интеграция явно не предусмотрена.

В первой версии в комнате выбирается одна основная игровая система, и этот выбор закрепляется навсегда; её `id` и `version` определяют системный модуль и системную принадлежность листов. Не поддерживать несколько одновременно активных основных систем и не менять закреплённую систему обычными командами.

- Использовать компактный типизированный реестр встроенных модулей и явные настройки включения/отключения. Не загружать сторонний исполняемый код, не создавать маркетплейс, динамический загрузчик или сложную систему плагинов.
- Настройки игровой системы комнаты и настройки дополнительных модулей отделяются от общих настроек комнаты.
- Отключение модуля скрывает его инструменты, но не удаляет автоматически сохранённую историю или данные.
- Сетка, когда она понадобится, подключается как необязательный Feature Module и по умолчанию выключена.

### Модуль `pbta-2d6`

Системный модуль содержит правила бросков и вычисление результатов. Бонус характеристики можно вводить вручную или подготовить из листа персонажа. Механика выносится в чистые функции, не зависящие от интерфейса, и принимает название характеристики, числовой бонус и ID персонажа/владельца. Не привязывать механику броска к заранее заданному набору характеристик.

Игровая комната при первоначальной настройке получает одну системную запись (`id` и `version`) либо явный режим без системы; после фиксации изменить выбор нельзя. Существующая комната мигрирует один раз с сохранением всех данных. Старые записи истории не получают выдуманную версию: они остаются историческими и не запускают текущую механику.

У каждого участника доступна компактная панель бросков с общей лентой. Панель располагается в правом нижнем углу доски, имеет собственную прокрутку и может сворачиваться; её состояние индивидуально для браузера. Скрытая панель показывает индикатор новых бросков. Новые записи идут сверху, без модального окна.

Обычный бросок:

`2d6 + введённый бонус`

Дополнительные параметры:

- **Превосходство:** +1 к итоговому результату.
- **Угнетение:** −1 к итоговому результату.
- **Помеха:** бросается 3d6, наибольший кубик отбрасывается, два оставшихся складываются; затем добавляется бонус и применимый модификатор.

Для Помехи бросать 3d6 и учитывать два наименьших кубика; бонус и ситуационный модификатор продолжают прибавляться. Превосходство и Угнетение — взаимоисключающие ситуационные модификаторы +1 и −1 соответственно, но оба могут сочетаться с Помехой.

### Интерфейс броска

- Поле ручного ввода бонуса (целое число, допускаются отрицательные значения).
- Селектор ситуационного модификатора: без модификатора, «Превосходство» или «Угнетение».
- Переключатель «Помеха».
- Кнопка броска.
- Ситуационный модификатор выбирается из трёх состояний: отсутствует, Превосходство (+1), Угнетение (−1).
- Помеха включается независимо и сочетается с выбранным ситуационным модификатором.
- После броска показывать исходные выпавшие значения, какие кубики были учтены, бонус, модификаторы, итоговую сумму и категорию результата; критический статус показывать отдельно.
- Бросок отправляется всем участникам в общую историю: имя игрока, результат, детали расчёта и время.
- Каждый игрок может бросать самостоятельно.
- Результат вычисляет сервер с использованием криптографически стойкого генератора случайных чисел Node.js, чтобы клиенты не могли подменить выпавшие значения.

### Результативные диапазоны

Результаты вычисляет системный модуль, а не ядро: итог до 6 включительно — «Неудача», от 7 до 9 — «Обычный успех», от 10 — «Триумфальный успех». Отдельно отмечать критический провал при двух учитываемых натуральных единицах и критический успех при двух учитываемых натуральных шестёрках. Критический статус определяется по результатам кубиков до модификаторов; при Помехе учитываются только два вошедших в сумму кубика.

### «Сила Судьбы» — повторный бросок

- Автор может повторить собственную проверку PbtA с тем же числом кубиков, бонусом, ситуационным модификатором и Помехой, но с новым независимым набором значений.
- Исходная запись остаётся неизменной; повтор сохраняется отдельной записью со ссылкой на исходный бросок и пометкой «Сила Судьбы».
- Не списывать и не проверять автоматически ресурс Силы Судьбы.

### Свободные броски

- Отдельный инструмент для бросков без категорий PbtA: 1–20 одинаковых кубиков форматов d4, d6, d8, d10, d12, d20 и d100.
- Показывать каждый результат и сумму. Все значения генерируются на сервере.
- Ведущий может выполнять свободные броски и проверки PbtA от имени выбранного игрока. Проверка использует те же правила PbtA и помечается именем ведущего и участника, за которого она выполнена. Самостоятельную проверку PbtA ведущий не выполняет.

### Генерация случайных значений и история

- Для всех бросков сервер использует `node:crypto` `randomInt()` и генерирует каждый кубик отдельно (`randomInt(1, sides + 1)`). Клиент передаёт только параметры; кубики, сумму, категорию и критический статус определяет сервер.
- Не принимать готовые значения кубиков и суммы. Для тестов генератор должен подменяться детерминированной функцией.
- В общей ленте показывать автора и участника броска, время, тип, выпавшие/учтённые кубики, отброшенный кубик, модификаторы, сумму, категорию, критический статус и связь повторного броска.
- Применения способностей показывать в той же ленте: имя игрока, персонаж, способность, компактная картинка, краткое описание и маркер «Применено». Полное описание раскрывается локально по кнопке.
- Хранить в SQLite только 10 последних событий всех типов, включая `ability-use`; при добавлении новой в одной транзакции удалять вышедшую за лимит запись. История сохраняется после перезапуска, не создавая архива, а связи `rerollOf` у оставшихся записей не изменяются.

## 11. Синхронизация в реальном времени

- Использовать WebSocket.
- Сервер является источником истины для общего состояния.
- При подключении клиент получает только разрешённую ему проекцию состояния комнаты.
- Изменения общего состояния рассылаются подключённым участникам.
- Во время перетаскивания допустимо отправлять промежуточные позиции с ограниченной частотой; окончательная позиция обязательно сохраняется по завершении действия.
- Состояние камеры и открытие/закрытие локальных окон не синхронизируются.
- Локальное открытие заметки не является общим событием.
- Фон комнаты и размеры меток входят в общую проекцию состояния; их изменения сохраняются в SQLite и рассылаются всем подключённым участникам.
- При переподключении клиент повторно получает актуальную разрешённую проекцию состояния.
- Если сервер отклоняет изменение из-за прав доступа, клиент возвращает объект к серверному состоянию и показывает понятное сообщение.

Не нужно реализовывать сложную CRDT-синхронизацию или совместное редактирование одного текста посимвольно. Для небольшой группы достаточно командного обновления состояния с проверкой прав на сервере.

## 12. Интерфейс и визуальный стиль

- Минималистичный интерфейс.
- Нейтральная палитра, чёткая типографика, аккуратные тонкие разделители.
- Без декоративных градиентов, тяжёлых теней и визуально шумных панелей.
- Рабочая область занимает основную часть экрана.
- Инструменты размещаются в компактной панели.
- Верхняя панель группируется по смыслу: «Вид доски», «Игровые инструменты», «Персонажи и материалы» и «Пользовательские действия». Группы разделены тонкими линиями; заметка и стикер объединены в меню «Создать».
- При нехватке ширины хвостовые группы переносятся в меню «Ещё»; горизонтальная прокрутка панели не появляется. Выпадающие меню имеют отступы 12–16 px, прокрутку при переполнении, позиционируются у границ окна и меняют сторону, если снизу не хватает места.
- Для стикеров, текста заметок, имён листов и описаний способностей доступны «Стандартный» шрифт и локальный Caveat. Caveat подключается из `public/fonts/` без CDN, с сохранением лицензии OFL; он не применяется ко всему интерфейсу.
- Панель слоёв доступна только GM.
- Панели заметок, персонажей и бросков открываются по запросу и не должны постоянно занимать большую часть экрана.
- Предусмотреть понятное состояние соединения: Online / Reconnecting / Offline.
- Предусмотреть индикатор сохранения: Saved / Saving / Error.
- Не делать сложный адаптивный мобильный интерфейс в первой версии. Интерфейс должен оставаться работоспособным на планшете, но приоритет — desktop.

## 13. Что не входит в первую версию

Чтобы не раздувать проект, пока не реализовывать:

- Голосовой и видеочат.
- Встроенные листы характеристик с автоматическими формулами.
- Автоматизацию разных НРИ, кроме базового модуля PbtA 2d6.
- Обязательную сетку.
- WebM и другие видеоформаты на доске.
- Сложный туман войны и динамическое освещение.
- Полноценное рисование кистью, фильтры и пиксельное редактирование.
- Сторонние плагины, маркетплейс и загрузку исполняемого кода.
- Облачную синхронизацию между разными серверами.
- Систему аккаунтов с электронной почтой.
- Веб-админку комнат и автоматическое полное восстановление установки одной командой.
- Динамическую загрузку системных модулей и перенос персонажей между комнатами (следующие этапы).

## 15. Этапы реализации

### Этап 1 — основа приложения и подключение

- Создать проект и базовую структуру.
- Запуск Fastify и раздача Astro frontend.
- Создать игровую комнату и роли GM/Player.
- Реализовать безопасное подключение по коду/паролю.
- Настроить WebSocket и статус подключения.
- Реализовать сохранение минимального состояния комнаты.

**Критерий готовности:** ведущий и два разных браузера игроков подключаются к одной комнате; сервер корректно различает роли; после обновления страницы соединение можно восстановить.

### Этап 2 — холст, изображения и слои

- Создать бесконечную рабочую область с личным pan/zoom.
- Добавить загрузку изображений и библиотеку ресурсов.
- Реализовать SHA-256 дедупликацию.
- Добавить размещение, перемещение, изменение размера, обрезку и отражение.
- Добавить GM-панель слоёв с перетаскиванием, видимостью, блокировкой и выбором активного слоя.
- Реализовать серверные права и фильтрацию скрытых слоёв.

**Критерий готовности:** ведущий размещает несколько изображений, в том числе несколько экземпляров одного ресурса; меняет порядок слоёв; игроки видят только разрешённые объекты и не получают GM-only данные.

### Этап 3 — интерактивные заметки и стикеры

- Добавить метки заметок.
- Добавить текст и изображения в заметки.
- Реализовать режимы доступа `gm-only`, `all-players`, `selected-players`.
- Обеспечить локальное открытие окна заметки.
- Добавить личные заметки игроков без меток и координат с доступом только для владельца и GM.
- Добавить текстовые стикеры и права их редактирования.

**Критерий готовности:** игрок не может получить закрытую или чужую личную заметку через интерфейс, API или WebSocket; открытие заметки одним участником не открывает её автоматически у других.

### Этап 4 — архитектура игровых модулей и первая игровая система

- Разделить встроенные System Modules и Feature Modules; реализовать компактный реестр модулей с идентификаторами и версиями системных модулей.
- Реализовать включение и отключение модулей без потери сохранённых данных и истории.
- Добавить настройку одной основной игровой системы для комнаты; её идентификатор выбирает активный системный модуль.
- Реализовать первый системный модуль PbtA: броски 2d6 + бонус, Превосходство, Угнетение и Помеху по согласованным правилам.
- Добавить общую историю бросков. Сохранить серверный расчёт результата с криптографически стойкой случайностью.
- Не реализовывать динамическую загрузку стороннего кода.

**Критерий готовности:** встроенный реестр различает системные и дополнительные модули; для комнаты однократно выбирается PbtA или режим без системы, сохраняются ID и версия, миграция существующей комнаты не теряет данные, а последующая смена системы отклоняется с понятным кодом. Игроки выполняют проверки и свободные броски, ведущий — свободные броски и проверки от имени игрока; сервер рассчитывает и рассылает одинаковые результаты. Повтор сохраняется отдельно, история SQLite переживает перезапуск и ограничена 10 записями. Отключение системы не удаляет её данные.

### Этап 5 — листы персонажей, связанные с игровыми модулями

- Реализовать лист PbtA как самостоятельную сущность с `creatorId`/`creatorName`, назначаемым `assignedPlayerId`/`assignedPlayerName`, фактическими `id`/`version` модуля `pbta-2d6` и версии схемы листа.
- Зафиксировать структуру листа в модуле: имя, портрет, четыре характеристики, «Сила Судьбы», произвольные счётчики и особые способности.
- Оставить хранение, синхронизацию и проверку прав общими механизмами ядра; не создавать универсальный конструктор.
- Связать характеристики с существующим окном броска и API PbtA без новой системы бросков.
- Разрешить игроку создавать несколько листов; созданный лист сразу назначается создателю. Ведущий создаёт несколько неназначенных листов и управляет назначением.
- Реализовать каталог с разделами «Мои персонажи»/«Другие персонажи» у игрока и полным списком у ведущего, с назначением, переназначением и снятием.
- Добавить режимы просмотра и редактирования: value-изменения доступны назначенному игроку и ведущему в просмотре, структурные — только в редактировании.
- Открывать лист плавающей панелью без блокирующей подложки и окно броска поверх неё; хранить положение, свёрнутость и открытость локально.
- Использовать существующую библиотеку изображений с SHA-256-дедупликацией и проверкой доступа; не копировать бинарники и не хранить их в SQLite.
- Выполнить безопасную миграцию прежней схемы с `owner_id`/`owner_name` и `UNIQUE(owner_id, system_id)`.

**Критерий готовности:** игрок создаёт несколько листов, которые сразу назначаются ему, и редактирует только назначенные; ведущий создаёт неназначенные листы, полностью заполняет их, назначает, переназначает и снимает назначение. Неназначенные листы не попадают к игрокам ни через API, ни через WebSocket. Назначенные листы видны всем в просмотре, но value- и структурные изменения проверяются сервером. Лист открывается в просмотре, переключается в редактирование отдельной кнопкой, плавает над доской и не блокирует поле; окно броска открывается поверх него и подготавливает существующий бросок PbtA с корректными названием, бонусом, ID персонажа/владельца и модификаторами; «Сила Судьбы» не списывается автоматически. Данные и изображения синхронизируются, переживают перезапуск, миграции не теряют данные, а локальное состояние (свёрнутость, положение, открытые окна) не попадает на сервер.

### Nechronica, этап 1 — независимый модуль, заглушки и боевая карта

**Статус: реализовано и покрыто автотестами. Полные правила Nechronica и боевые механики не входят в этот этап.**

**Системный модуль.**

- `src/modules/system/nechronica/module.ts` регистрирует `id: 'nechronica'`, `version: '1.0.0'`, `name: 'Nechronica'`, `sheetSchemaVersion: 1`.
- `src/modules/registry.ts` хранит системные версии, отдаёт `sheetSchemaVersion` и функцию `findSystemModule(id, version)`. PbtA и Nechronica — независимые записи реестра.
- Листы фильтруются в `RoomStore` по закреплённой системе и версии. После фиксации нельзя создать, изменить, назначить или удалить лист другой системы; сами листы сохраняются и скрываются из обычных API.
- Лист Nechronica создаётся с пустым `characteristics_json = {}`; `hydrateSheet` не подставляет PbtA-нули не-PbtA листам. Команды `sheet:fate:update`, `sheet:counter:*`, `sheet:ability:*` и поля `characteristics`/`fate` в `sheet:update` требуют PbtA-лист и иначе отклоняются с ошибкой.
- Общие поля листа (имя, портрет, шрифт, назначение игроку, режим просмотра, закрытие) работают одинаково. Панель Nechronica показывает заглушку «Лист персонажа Nechronica — находится в разработке»; PbtA-характеристики, счётчики и способности не отрисовываются.
- Меню бросков Nechronica показывает заглушку «Система бросков Nechronica — находится в разработке», не содержит полей PbtA, не вызывает PbtA-механику и не создаёт записей в `dice_rolls`.
- Система закрепляется один раз; смена системы недоступна через интерфейс, HTTP, WebSocket или обычные серверные методы. Листы другой системы не преобразуются и не удаляются. История бросков остаётся общей, а записи без совпадающей системной атрибуции показываются как исторические.

**Сцены и боевая карта.**

- Введены тип `BoardScene = 'board' | 'battle'` и `BoardSceneSnapshot`. Сцена — отдельный набор данных, а не фильтр видимости.
- Схема БД: `room.active_scene` (`board`/`battle`, по умолчанию `board`), `room.battle_background` (`gray`/`black`, по умолчанию `gray`) и `board_layers.scene` (`board`/`battle`, по умолчанию `board`). Индекс `board_layers_scene_order(scene, order_index)`.
- Миграции аддитивные: колонки добавляются через `ALTER TABLE ... DEFAULT`, затем создаётся индекс и недостающие слои для обеих сцен. Старые слои, объекты, стикеры и метки остаются на основной доске.
- Объекты, стикеры и метки наследуют сцену через `layer_id`; отдельные колонки сцены им не нужны.
- `RoomStore.snapshot` формирует поля активной сцены в прежних ключах (`background`, `layers`, `objects`, `stickers`, `noteMarkers`) и добавляет `activeScene`. Ведущему добавляется `battle` с полным содержимым боевой карты только при `capabilities.battleMap = true`; игрок поле `battle` не получает.
- `SystemModuleDescriptor.capabilities.battleMap` — типизированная возможность модуля: Nechronica `true`, PbtA `false`. Снимок отдаёт `system.capabilities`. Клиент не создаёт кнопки и предпросмотр без возможности, а сервер проверяет её через закреплённую систему и реестр; клиентские `systemId`/`capabilities` не учитываются. В PbtA `room:scene:set` и `room:background:set` со сценой `battle` отклоняются с `409 SYSTEM_MISMATCH`, а старая активная сцена `battle` безопасно открывается как `board` с сохранением данных.
- `room:scene:set` — глобальная команда только для ведущего; сервер проверяет роль, допустимое значение и отсутствие лишних полей. `room:background:set` принимает необязательное поле `scene`, фон хранится отдельно для каждой сцены.
- Команды `layer:*`, `object:*`, `note-marker:*`, `sticker:*` и `room:background:set` принимают необязательное поле `scene`. Игрок может менять только активную сцену; ведущий — любую. Без поля используется активная сцена.
- `canReadAsset` и публичные объекты учитывают сцену: ресурс боевой карты недоступен игроку, пока боевая карта не активна.
- GM-предпросмотр боевой карты — локальное клиентское состояние `viewingBattle`, без серверной команды. Клиент явно отправляет `scene: 'battle'` для команд, пока сцена не активна; игроки продолжают видеть активную сцену. Баннер предпросмотра не переключает участников.
- Камеры и активный слой хранятся в localStorage отдельно по ключу сцены. После переподключения сервер отдаёт актуальную активную сцену, клиент восстанавливает камеру этой сцены. Камеры не синхронизируются между участниками.
- Удаление ресурса проверяет все ссылки, включая объекты обеих сцен, вложения заметок, портреты и изображения способностей. Backup/restore сохраняют `active_scene`, `battle_background`, слои и объекты обеих сцен и связанные изображения.
- `server/nechronica-battle.test.ts` покрывает реестр, изоляцию листов и PbtA-команд, независимость сцен, ACL боевой карты, отказ игроку в `room:scene:set`, возврат активной сцены после переподключения и backup/restore.

**Ограничения и отложенное.**

- Nechronica: полные правила, структура листа, характеристики, счётчики, способности и броски не реализованы.
- Боевая карта: нет сетки, токенов, инициативы и специализированных боевых бросков; доступны только общие инструменты доски (изображения, слои, стикеры, метки).
- Предпросмотр боевой карты и камеры требуют ручной проверки в браузере: автоматических end-to-end тестов нет.

### Закрепление системы комнаты (этап 2)

**Статус: реализовано и покрыто автотестами. Многокомнатная архитектура не входит в этап.**

**Схема и миграция.**

- `room.system_id`, `room.system_version`, `room.module_config_json` и `room.system_fixed` заменяют изменяемую пару `active_system_id/version`.
- `system_fixed = 0` — система ещё не выбрана; `system_fixed = 1` при `id = NULL` и `version = NULL` — намеренный режим «без системы».
- Миграция старой базы переносит `active_system_id/version` только при полной известной паре. Частичная пара или неизвестный модуль дают понятную ошибку без фиксации; при обоих `NULL` выбор остаётся за ведущим. Повторный запуск идемпотентен и сохраняет ID, листы, объекты, ресурсы, заметки, броски, назначения и историю.
- SQLite-триггеры `room_system_immutable`, `room_system_fixed_immutable`, `room_legacy_system_immutable` и `room_system_pair_update` запрещают обычную смену закреплённых полей и частичную пару ID/версии. Контролируемая будущая миграция версии должна явно снять триггер в собственной транзакции.

**API, WebSocket и UI.**

- Одноразовая фиксация: `room:system:initialize` по WebSocket и `PUT /api/room/system` по HTTP. Повторная попытка и устаревшая `room:system:set` возвращают `409 ROOM_SYSTEM_IMMUTABLE`.
- Несовпадение системной механики или листа возвращает `409 SYSTEM_MISMATCH`.
- Снимок комнаты отдаёт `system: { fixed, id, version, name, config }` вместо `activeSystem`. Селектор виден только при `fixed = false`; после фиксации показываются только название и версия.

**Данные и история.**

- Листы другой системы не удаляются и не преобразуются, но скрываются из `room:state`, `GET /api/sheets`, `GET /api/sheets/:id`, обычных списков и редактирования. Архивы комнат не реализованы.
- Новые системные броски и применения способностей получают `system_id/system_version` только от сервера. Свободные броски хранятся с `NULL/NULL`.
- Старые `pbta`/`ability-use` записи классифицируются как `pbta-2d6` без версии; `free` остаются `NULL/NULL`. Записи без совпадающей атрибуции показываются как «Историческая запись», не запускают механику и не повторяются через текущую систему. Лимит 10 последних событий не изменён.

**Проверки.**

- `server/system.test.ts` покрывает миграцию копии реальной базы, идемпотентность, сохранение ID, режим «без системы», триггеры, отказы HTTP/WS, изоляцию листов и истории, атрибуцию бросков и backup/restore.
- Ручная проверка комнат Nechronica/PbtA после перезапуска, попыток смены системы, листов/истории и двух браузеров остаётся финальным чек-листом.

### Изоляция данных комнаты и подготовка многокомнатности (этап 3)

**Статус: реализовано и покрыто автотестами. Несколько комнат, каталог комнат и многокомнатная авторизация не реализованы.**

**Хранение и миграция.**

- Целевая раскладка: `data/rooms/default/{room.sqlite,assets,backups}`; `APP_DATA_DIR` остаётся корнем приложения. Постоянный ID `default` записан в `data/storage.json` вместе с версией раскладки и не генерируется при запуске.
- `server/room-storage.ts` — единственное место преобразования корня данных в каталог комнаты. При наличии старого `data/room.sqlite` без маркера сервер отказывается стартовать.
- `npm run room:migrate` (`server/room-migrate.ts`) выполняется при остановленном сервере: создаёт полную копию рядом с `data/`, переносит SQLite через backup API, копирует assets и backups без изменения содержимого, проверяет `integrity_check`, `foreign_key_check`, количество строк, наличие/размеры/SHA-256 ресурсов, открывает `RoomStore` и создаёт проверочную копию. Маркер пишется последним, старые файлы не удаляются, повторный запуск идемпотентен, частичный destination даёт понятную ошибку.

**RoomStore и ресурсы.**

- `RoomStore(roomDir, roomName)` хранит собственные `roomDir`, `assetsDir`, `backupsDir`; БД, изображения и копии принадлежат экземпляру. Общих изменяемых module-level путей нет.
- `saveImageAsset`/`deleteImageAsset` принимают каталог ресурсов явно; SHA-256-дедупликация и уникальность `(sha256, mime_type)` действуют внутри комнаты. Выдача файла и удаление проверяют БД и ссылки текущего экземпляра.
- Backup/restore работают с каталогом комнаты; манифест `version: 1` совместим со старыми копиями.

**Участники и сессии.**

- `participants(id, name, role, created_at)` отделена от `sessions(id, participant_id, expires_at, created_at)`. Один участник может иметь несколько сессий, закрытие одной не затрагивает другую; повторный вход с тем же именем/ролью переиспользует участника.
- Миграция старых `sessions` создаёт `participants` с теми же ID, поэтому `assigned_player_id`, `creator_id`, `owner_id`, `asset_uploaders.participant_id` и `dice_rolls.author_id/actor_id` сохраняют ссылки.
- WebSocket по-прежнему ключуется ID сессии, но `participants` в `room:state` дедуплицируются по `participantId`; соединение хранит участника, сессию и (в будущем) идентификатор комнаты.

**Боевая карта.**

- `capabilities.battleMap` объявлена в `SystemModuleDescriptor`; Nechronica — `true`, PbtA — `false`. Сервер проверяет возможность через `RoomStore.supportsBattleMap`, а не доверяет клиенту.
- В PbtA отсутствуют кнопка, меню и предпросмотр; `room:scene:set`/`room:background:set` со сценой `battle` и команды доски с `scene: 'battle'` отклоняются. Подмена `systemId` или лишние поля команды не обходят проверку. Старая сцена `battle` переводится на `board` без удаления слоёв и объектов.

**Ограничения этапа.**

- `catalog.sqlite`, CLI комнат, многокомнатная cookie-модель, LRU RoomStore, динамическая загрузка модулей и перенос листов между комнатами не реализованы.
- `ROOM_CODE`, `GM_PASSWORD`, `ROOM_NAME` остаются в `.env`; URL входа и порядок запуска не менялись.
- Ручная проверка входа GM/двух игроков, переподключения, PbtA, Nechronica, боевой карты, изображений, заметок, листов и backup/restore остаётся финальным чек-листом.

### Многокомнатность (этап 4)

**Статус: реализовано и покрыто автотестами. Динамическая загрузка модулей и веб-админка не реализованы.**

**Каталог и секреты.**

- `data/catalog.sqlite` — таблица `rooms` с `id`, `name`, `system_id`, `system_version`, `room_code_hmac`, `gm_password_hash`, `status` (`active`/`disabled`/`archived`), `created_at`, `updated_at`.
- `data/server-secret` — 32+ случайных байта, права `0600`, создаётся только при инициализации. Каталог без секрета даёт понятную ошибку и не перегенерирует секрет.
- Код комнаты хранится как HMAC-SHA256; новый код — 8 символов из `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`. Короткие коды нормализуются (trim/регистр), старые длинные коды сохраняют регистр. HMAC уникален.
- Пароль GM — scrypt с индивидуальной солью, проверка constant-time; открытый пароль не пишется в каталог, логи, CLI-вывод и клиент.
- Ошибки входа нейтральны, попытки ограничены rate limit; комнаты не перечисляются.

**CLI.**

- `npm run rooms:init` идемпотентно регистрирует существующую `rooms/default` из `.env`; не меняет код, пароль, имя или систему; не печатает секреты.
- `npm run rooms:create -- --name "..." --system pbta-2d6|nechronica` создаёт каталог атомарно, фиксирует систему, печатает код один раз; пароль вводится скрыто или строкой stdin.
- `rooms:list` не показывает коды/HMAC/хэши. `rooms:disable`, `rooms:enable`, `rooms:archive` меняют статус; архив создаёт финальную копию, закрывает соединения и сохраняет данные.
- `rooms:delete` удаляет каталог комнаты и запись каталога. Активная или отключённая комната требует `--force`; архивная удаляется без него. Подтверждение — точный ID комнаты либо `--yes`. По умолчанию создаётся финальная копия, а все backups переносятся в `data/deleted-rooms/<id>-<время>/` с `room.json`; `--no-backup` отключает только новую финальную копию. Копию удалённой комнаты можно восстановить в новую комнату той же системы через `backup:restore --accept-room-mismatch`.
- Изменения статуса из CLI видны работающему серверу без перезапуска.

**RoomManager.**

- Ленивое открытие `RoomStore` по явному каталогу комнаты; проверка статуса и системной пары каталога/базы; защита path traversal.
- LRU, refcount/leases для HTTP и WebSocket, лимит `MAX_OPEN_ROOMS`; при переполнении — `RoomCapacityError`. `RoomManager.close()` закрывает комнаты и каталог.
- Глобального «текущего RoomStore» нет. Для тестов сохранён совместимый `SingleRoomAccess`, production использует `CatalogRoomAccess`.

**Авторизация и клиент.**

- Код комнаты выбирает `RoomStore`; пароль GM проверяется только для GM. После входа клиент переходит на `/room/<room-id>`.
- Cookie `tb_session_<roomId>`: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` при HTTPS. Logout одной комнаты не трогает другие.
- Один браузер — несколько комнат в разных вкладках. Ключи `localStorage` включают `roomId`: камера, zoom, панели, открытый лист, прочитанные события, тема.
- HTTP/WS полностью изолированы по комнатам; `roomId` из клиента сверяется с каталогом и сессией; изображения дедуплицируются внутри комнаты, чужие ID недоступны, удаление проверяет ссылки.

**Backup.**

- `npm run backup -- --room <id>`, `backup:list -- --room <id>`, `backup:restore -- --room <id> <имя>`.
- Manifest v2: `roomId`, `roomName`, `systemId`, `systemVersion`, `schemaVersion`, checksums. Restore проверяет комнату и систему, создаёт `pre-restore-*`. v1 читается и восстанавливается с явной комнатой.
- `catalog:backup` копирует `catalog.sqlite` + `server-secret`; `install:backup` — полную установку. Restore каталога — только при остановленном сервере; полное восстановление установки — документированная ручная операция.

**Миграция `default`.**

- `npm run room:migrate` переносит старую раскладку в `data/rooms/default/`, затем `npm run rooms:init` регистрирует её в каталоге.
- После инициализации обычный сервер не требует `ROOM_CODE`, `GM_PASSWORD`, `ROOM_NAME`; `.env` автоматически не изменяется.
- Старые сессии не переносятся: пользователи один раз входят заново под новой комнатной cookie.

**Ограничения этапа.**

- Нет динамического `import()` системных модулей: PbtA и Nechronica статически импортируются.
- Нет веб-админки, переноса персонажей/листов между комнатами, конвертации систем и нескольких систем в одной комнате.
- `rooms:delete` необратим для рабочих данных, но сохраняет копии в `data/deleted-rooms/`; полное освобождение места требует ручного удаления этого каталога. Удаление лучше выполнять при остановленном сервере.
- Визуальная вёрстка и Konva требуют периодической ручной проверки; автотесты и CDP-проверка покрывают логику, cookie и изоляцию.

## 16. Критерии качества и приёмки

Приложение считается пригодным для первой игровой сессии, когда:

1. GM и 3–6 участников могут одновременно подключиться к одной комнате.
2. Все видят изменения общей доски без ручного обновления страницы.
3. У каждого участника собственное положение и масштаб камеры.
4. GM может создавать, сортировать, скрывать и блокировать слои.
5. Игроки не видят список слоёв и не получают содержимое GM-only областей.
6. Одно изображение можно разместить несколько раз без повторной загрузки бинарного файла.
7. Изображения можно двигать, масштабировать, обрезать и отражать.
8. Заметки открываются локально и проверяют права на сервере.
9. В комнате выбирается одна основная система один раз; её системный модуль определяется идентификатором и версией из встроенного реестра и после фиксации не меняется. Feature Modules не меняют механику системы без явной интеграции.
10. PbtA использует указанные категории и критические результаты; сервер генерирует кубики, вычисляет результат и сохраняет данные. Свободные броски не получают категории PbtA.
11. Листы — самостоятельные сущности с создателем и назначаемым игроком; структура PbtA включает имя, портрет, четыре характеристики, «Силу Судьбы», счётчики и способности; назначение и права проверяются сервером.
12. Игрок может иметь несколько листов; ведущий создаёт неназначенные листы, назначает и снимает назначение. Неназначенные листы не передаются игрокам. Назначенные видны всем для просмотра, но редактируют их только назначенный игрок и ведущий. Характеристики готовят существующий бросок PbtA, «Сила Судьбы» не списывается автоматически, а локальное состояние листа не синхронизируется.
13. После перезапуска сервера основные данные и изображения сохраняются.
14. Сборка production проходит без ошибок, TypeScript не содержит необъяснённых ошибок, основные проверки проходят.
15. `npm start` запускает собранный frontend, API и WebSocket на одном порту; неизвестные маршруты и ошибки обрабатываются предсказуемо.
16. Публичный HTTPS-origin явно разрешается через `PUBLIC_ORIGIN` или корректно настроенный `TRUST_PROXY`; произвольный Origin и подмена `X-Forwarded-*` без доверия прокси не проходят. Cookie остаются `HttpOnly`/`SameSite=Strict`, а `Secure` включается при HTTPS.
17. Резервная копия включает согласованный SQLite-снимок и все изображения; восстановление проверяет копию, создаёт страховочную копию и не оставляет частично заменённых данных.
18. `data/`, `.env`, `.sqlite`, изображения и резервные копии не попадают в Git.
19. Фон доски переключается только ведущим, одинаков у всех участников и восстанавливается после перезапуска; смена фона не меняет камеру и содержимое доски.
20. Неназначенный лист удаляется ведущим вместе со счётчиками и способностями; назначенный лист удалить нельзя; изображения библиотеки сохраняются.
21. Неиспользуемый ресурс удаляется вместе с оригиналом и производными файлами; используемый ресурс защищён проверкой всех типов ссылок, а ошибка файловой системы не оставляет потерянных записей или файлов.
22. Метки заметок меняют размер на доске, текст переносится без изменения шрифта, изображения сохраняют пропорции, заблокированный слой запрещает изменение, а отмена возвращает прежний размер.
23. Личные заметки игроков не имеют меток и координат; игрок управляет только своими записями, GM видит все записи только для чтения. Чужой игрок не получает ни список, ни текст, ни изображения даже прямым запросом, а общая рассылка комнаты не содержит приватного содержимого.
24. Изображение без разрешения на перемещение у игрока не перехватывает указатель и не блокирует объекты под ним; камера панорамируется прямо над изображением, а выбор ведущего по активному слою сохраняется.
25. Nechronica зарегистрирована как независимая система; её лист и меню бросков показывают заглушки, не используют характеристики, формулы и обработчики PbtA и не создают PbtA-броски. Система выбирается один раз; после фиксации листы другой системы сохраняются, но скрыты из обычных API и не редактируются, а старые броски без полной системной атрибуции показываются как исторические.
26. Боевая карта — отдельная сохранённая сцена с собственными слоями, объектами, стикерами, метками и фоном, доступная только системе, которая объявляет `capabilities.battleMap` (Nechronica). Пока карта не вызвана, игрок не получает её содержимое и GM-only данные; вызов и возврат доступны только ведущему, а PbtA не может включить сцену `battle` ни через интерфейс, ни прямой командой.
27. Камеры участников локальны и раздельны для основной доски и боевой карты; после переподключения каждый видит актуальную активную сцену со своей камерой. Удаление ресурсов учитывает ссылки боевой карты, а backup/restore сохраняет обе сцены.
28. Один сервер обслуживает несколько комнат; каждая имеет собственные SQLite, ресурсы, сессии, листы, заметки и историю. Каталог содержит только метаданные и не хранит игровые данные.
29. Код комнаты хранится как HMAC с `server-secret`, пароль GM — как scrypt-хэш. Ошибки входа нейтральны, попытки ограничены, секреты не выводятся в CLI и логи. Каталог без секрета не открывается.
30. `rooms:create/list/disable/enable/archive/delete` работают без перезапуска сервера; создание атомарно, код показывается один раз, архив создаёт финальную копию и сохраняет данные, удаление требует подтверждения и оставляет копии в `data/deleted-rooms/`.
31. `RoomManager` открывает комнаты лениво, проверяет статус и систему, ограничивает число открытых баз и закрывает простаивающие. Cookie и `localStorage` привязаны к комнате; logout и ошибка в одной комнате не влияют на другие.
32. Backup комнаты (manifest v2) проверяет `roomId` и системную пару; копия каталога включает `catalog.sqlite` и `server-secret`; полная копия установки создаётся и проверяется. Restore каталога выполняется только при остановленном сервере.
33. Существующая `default` регистрируется идемпотентно, её код/пароль/система не меняются, а обычный запуск после этого не требует `ROOM_CODE`, `GM_PASSWORD`, `ROOM_NAME`.

## 17. Нерешённые детали и принятые допущения

Чтобы не блокировать старт разработки, в первой версии приняты следующие решения:

- **Помеха:** в модуле PbtA бросить 3d6 и сложить два наименьших кубика. Бонус характеристики и ситуационный модификатор сохраняются.
- **WebM:** не входит в первую версию; статичные PNG/JPG/JPEG/WebP важнее.
- **Права игроков на доске:** по умолчанию игроки не редактируют произвольные объекты ведущего; ведущий может разрешать перемещение отдельных объектов, а создание собственных стикеров игроками можно включить отдельно.
- **Комнаты:** один сервер обслуживает несколько комнат. Существующая `default` мигрируется и регистрируется идемпотентно; новые комнаты создаются CLI. Система каждой комнаты закрепляется один раз, а старые листы другой системы скрываются без удаления. Перенос листов между комнатами и конвертация систем не реализованы.
- **Сетка:** отсутствует в ядре и выключена; позднее подключается модулем.
- **Публичность листа:** назначение — единственное основание прав игрока. Назначенные листы видны всем участникам, редактируют их назначенный игрок и ведущий; неназначенные видит только ведущий. Создатель-игрок без назначения прав не сохраняет. Модель прав общая, а содержание и структура листа зависят от системного модуля.
- **ngrok:** публичный адрес задаётся через `PUBLIC_ORIGIN`; при бесплатном тарифе он меняется после перезапуска туннеля. `TRUST_PROXY=true` остаётся опцией для случая, когда сервер доступен только через локальный прокси, и по умолчанию выключен.
- **Резервные копии:** восстановление выполняется только при остановленном сервере. Приложение проверяет копию и создаёт `pre-restore-*`, но не управляет внешним хранением и ротацией старых копий.
- **Фон доски:** доступны только серый и чёрный; серый сохраняет прежний фон по умолчанию. Значение хранится в `room.background`.
- **Удаление листов и ресурсов:** физические изображения не удаляются вместе с листом. Ресурс удаляется только при отсутствии фактических ссылок; принудительное удаление не предусмотрено.
- **Размеры меток:** `note_markers.width`/`height` хранятся явно. Для старых записей миграция вычисляет прежние размеры и заполняет колонки без изменения координат.
- **Сцены:** у комнаты ровно две сцены — `board` и `battle`. Сцена задаётся слоем (`board_layers.scene`), а объекты, стикеры и метки наследуют её через слой. `room.active_scene` — общая активная сцена; `room.battle_background` хранит фон карты отдельно от `room.background`.
- **Предпросмотр боевой карты:** локальное состояние ведущего, не команда и не отдельный режим сервера. Игроки не получают `battle`, пока карта не активирована; ведущий получает его только в комнате, где закреплённая система объявляет `capabilities.battleMap`.
- **Права на сцены:** игрок может менять только активную сцену; ведущий — любую. Вызов и возврат карты — только ведущий. Проверки выполняются на сервере, а не только скрытием интерфейса.
- **Камеры сцен:** pan/zoom и активный слой хранятся в localStorage отдельно для каждой сцены и не синхронизируются. После переподключения клиент применяет камеру актуальной активной сцены.
- **Nechronica:** на первом этапе система независима от PbtA, но её механика и структура листа ещё не определены. Лист создаётся с пустым набором характеристик, PbtA-команды для него отклоняются. Полные правила, сетка, токены, инициатива и боевые броски отложены.
- **Ресурсы и backup:** удаление ресурса проверяет ссылки обеих сцен; резервная копия сохраняет сцены, их фон и активную сцену.

Эти решения не должны мешать последующему расширению приложения.
